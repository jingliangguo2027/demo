# 产品方向与技术选型

记录日期：2026-10-10。状态：本会话的阶段性讨论记录，尚未形成完整产品需求或最终架构。

“明确”记录用户已表达的方向；“倾向”记录用户当前偏好；“建议”记录助手提出的方案；“待定”表示仍需讨论或验证。下列产品、训练和性能方案均未实现或实测。

## 1. 产品方向

| 项目 | 暂时结论 | 状态 |
| --- | --- | --- |
| 产品定位 | 吃喝玩乐参谋与找房助手是两个独立的领域 Agent；可以复用工程组件，但不合并为通用 Agent | 明确 |
| 游戏方向 | NPC 长期记忆仍有兴趣，但游戏内容与实现范围太大，当前暂时放下 | 当前倾向 |
| 核心目标 | 持续跟进用户，从行为、交流和体验反馈中理解需求，提供合适的建议与帮助 | 明确 |
| 目标痛点 | 用户有主观目的，但难以表达需求或判断取舍；具体目标用户和痛点尚未选定 | 方向明确，具体待定 |
| 产品交互 | 支持自然语言交流，也通过气泡、简单选项和候选比较降低表达门槛 | 明确 |
| 主动性 | 根据历史、当前行为、日期和时间等提出需求假设，用户可确认、纠正或跳过 | 明确方向，策略待定 |
| 与搜索和推荐的关系 | 倾向于配合候选检索与排序，增加需求澄清、比较解释、任务推进和反馈闭环 | 当前倾向，分工待定 |
| 首个产品 | 吃喝玩乐与找房之间尚未选择；没有决定同时开发两个完整产品 | 待定 |

核心循环：**经历与交流 → 用户理解 → 合适的建议或问题 → 用户决策与体验 → 记忆更新 → 下一次帮助。**

## 2. 主动交互

用户提出的例子：周五晚上，结合用户以往这个时段的行为，主动询问“怎么说，今晚喝两口？”。这是交互设想，不代表真实用户的动机已被验证。

| 条件 | 建议交互 |
| --- | --- |
| 依据充分，当前时机也合适 | 提出具体建议，提供确认、纠正和跳过选项 |
| 有几个合理方向，需要区分 | 问一个直接帮助当前选择的小问题 |
| 依据不足，提问收益也不明显 | 保持普通浏览，等待更多信号或用户主动开口 |

- 示例选项：`安排一下` / `只吃不喝` / `先逛逛`。多个候选可以同时合理，优先展示一个合适提议，其他作为较轻的入口。
- 置信度与“是否值得主动开口”分别考虑；触发策略还应考虑近期拒绝、重复提议和打扰频率。
- 信息不足不必自动追问；问题应帮助当前决策，而非要求用户填写画像。
- 点击、忽略或关闭气泡不能直接证明原始动机或长期偏好；接受提议也可能是被启发后产生的新需求。
- 置信度的预测对象、校准方式、阈值、语气偏好和触发频率均待定。

## 3. 用户建模与记忆

用户提出的主线：结合行为推断与聊天内容形成用户模型，用记忆和上下文组装支撑后续决策。以下信息划分为建议，字段和更新规则尚未确定。

| 信息 | 内容 | 处理原则 |
| --- | --- | --- |
| 行为事实 | 展示、点击、收藏、拒绝、下单等实际事件及场景 | 保存实际依据，不直接等同于偏好 |
| 明确表达 | 用户说过的需求、理由、约束和纠正 | 保留主体、时间、条件和适用范围 |
| 模型推测 | 当前意图、潜在偏好、行为原因 | 标记为假设，附证据，允许修订 |
| 体验与结果 | 接受或拒绝原因、实际体验、满意或失望 | 区分交易完成与需求满足 |

临时意图与长期偏好分别处理；既学习用户喜欢什么，也学习用户希望怎样被帮助。保留来源、变更与纠正依据，避免一次行为形成永久标签。

会话架构尚未确定。助手建议：前端保留连续的助手入口，底层分别管理领域内的用户记忆、持续任务和当前交互；长期记忆可独立于会话存在。单会话与跨会话的具体范围、数据归属和删除语义仍需确定。

TP 暂不作为每次推荐或交易的必需产物。普通点餐可记录轻量经历；找房、多人大型聚餐等需要反复比较的过程可考虑任务材料集合。是否采用及具体结构待定。旧文档中的 TP 是按功能/主题增量组织材料的目录，不等同于交易结束后打包。

## 4. 技术选型

| 部分 | 当前方案 | 决策状态与职责 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite + Pinia | Vue 为用户明确选择；其余为配套建议。实现聊天、气泡、候选卡片与反馈 |
| 业务后端 | Spring Boot | 用户倾向；负责用户、鉴权、行为记录和业务接口 |
| Agent 框架 | LangGraph + 按需使用 LangChain | 用户倾向；分别负责流程与恢复、模型和工具适配 |
| Agent 服务 | Python + FastAPI | 助手建议，尚未最终锁定。用户可接受 Python 或 TS，且已熟悉 Python；Python 便于衔接训练、数据处理和评测 |
| 数据与检索 | PostgreSQL + pgvector | 助手建议；保存事件、用户模型、任务状态并支持向量检索。关键词/BM25 与向量融合的具体实现待定 |
| 缓存与限流 | Redis | 用户提出组件；缓存、限流、短期数据等职责为助手建议，持久记忆以数据库为准 |
| 异步任务 | RabbitMQ | 助手建议，按后台任务需求引入；任务确认、重试与幂等规则待实现 |
| 部署与监控 | Docker Compose 起步；OpenTelemetry + Prometheus/Grafana | 助手建议；具体部署规模、组件版本和资源预算待定 |

LangGraph 的流程检查点与产品的用户记忆分别管理。偏好推断、记忆更新、证据选择和 Context Builder 仍需自行设计与验证。

高并发、高可用是用户明确的工程目标，当前尚无性能承诺。计划验证异步执行、模型并发上限、排队、限流、幂等、有限重试和断线恢复；基础链路稳定后再验证多实例与数据库/队列故障切换。

接口吞吐与模型生成能力分别测量，指标包括同时生成数量、首字延迟、整体延迟、错误率，以及重启和重复消息下的恢复结果。

## 5. 后训练与模型

用户倾向于 LoRA 等轻量方案，当前算力不支持将全量微调作为主线。助手建议首轮使用 **SFT + LoRA**，资源紧张时评估量化 LoRA；具体训练任务、数据和目标尚未确定。

- 候选训练点：临时意图与长期偏好的区分、有依据的记忆更新、纠正与冲突处理，以及建议/提问/等待的交互选择。
- 用户具体经历由外部记忆保存；训练学习通用判断方式，记忆更新与模型权重更新分别进行。
- 当前本机已读取为 Apple M5、24GB 内存。建议用 MLX-LM 做本地实验；需要 CUDA 时再评估 PyTorch + Transformers + TRL + PEFT。尚无模型兼容性、训练占用或速度实测。

| 生成模型候选 | 建议角色 |
| --- | --- |
| Qwen3.5-4B | 优先测试的小模型候选 |
| Qwen3-4B-Instruct-2507 | 纯文本、非思考模式的训练与推理对照 |
| Qwen3.5-9B | 检查增加规模能否带来值得的收益 |

上述均为候选，未下载、训练或完成项目评测。Embedding 模型、推理引擎、量化格式和具体版本仍待选择。行业事实通过业务数据和检索提供。

真实数据是主要未决问题。拟先跑通产品，再收集完整决策过程，包括展示候选、排序位置、价格/优惠、行为、表达理由和后续体验。合成与人工审核案例可验证流程和训练局部能力，不能代替真实用户效果验证；下单或签约不能直接作为意图推断正确、用户满意的标签。

## 6. 下一轮优先明确

1. 选择首个领域、目标用户、具体决策场景与成功标准。
2. 确定可获取的业务数据、行为事件、反馈和最小记忆结构。
3. 确定主动交互的触发、纠正和停止机制，以及评测方式。
4. 确定会话与记忆归属、Agent 服务语言、模型候选和训练任务。

最小工程链路建议：**Vue → Spring Boot → Agent 服务 → 模型 → 流式返回**，随后接入行为记录与记忆更新。该顺序是建议，尚未开始搭建。
