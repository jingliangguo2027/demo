# 第一版后深入研究计划

> 修订日期：2026-10-12。版本：`v1.0-research-plan`。状态：研究计划，尚未取得本项目实验结论。
>
> 本文与[第一版实现计划](./第一版实现计划.md)、[数据源调研与使用计划](./数据源调研与使用计划.md)同步。本次未能重新读取仓库内原同名文件，因此这是依据本会话完整方案编写的同名配套重写稿，不声称完整保留了未取得原文中的每个研究条目；提交前应查看差异并保留额外的既有内容。
>
> 核心原则：**第一版先有能运行、能观察、能回放的完整基础系统；后续每次围绕一个问题修改策略，在隔离数据和同等条件下验证。** 本文件列的是待验证假设，不是对某个方案更优的承诺。

## 1. 第一版已经包含什么，不再留到研究阶段补工程基础

第一版必须有 Raw、当前事实和版本、CTS、固定 Raw 区间 Episode、轻量 TP、固定双路检索、四层 Context Builder、大工具结果外置、受控跨会话、运行快照、回放/评分、隔离 Namespace、持久作业、重启与删除屏障。

这些模块的**基本正确性**不能通过“以后研究”推迟：新输入不丢、当前版本不被旧摘要覆盖、原文可回查、标签不泄漏、删除后不写回、实验不串数据、未知成本不填零。后续研究比较的是在这些规则不变时如何提取、压缩、检索、选择和学习。

四个首版基线：A 最近窗口；B 普通滚动摘要；C 核心不带 TP；D 核心加 TP。它们应都真实运行。A/B 没有的内部事实指标记 N/A，主比较使用共同的后续任务与总成本。

## 2. 何时开始某一项研究

先通过主计划 T01—T28 工程验收，并有人工轨迹和小批 MemOps 的真实运行记录。某个模块存在消息丢失/数据库竞争等工程错误时，先修工程再评算法；否则实验无法解释。

开始一项研究前应写明：问题、一个主要变量、基线、固定项、数据来源与用途、评分规则、预算、预计可能失败的情况、停止/接纳条件。预计收益只能写成假设，不提前写提升百分比。

每次运行必须保存代码/配置/提示词/数据/评分版本、实际输入与输出，以及价格和用量来源。API 别名或随机种子不保证完全复现，结果复查依靠完整记录。

## 3. 研究路线总表

编号使用 `EXP-`，避免与仓库既有调研任务编号混淆。

| 顺序 | 项目 | 核心问题 | 首要数据 | 需要控制的变量 |
| --- | --- | --- | --- | --- |
| 1 | EXP-01 记忆更新与提交 | 是否正确新增、替换、保持，能否区分时间/范围/主体 | 人工 + MemOps | 回答模型、检索、预算、提交器 |
| 2 | EXP-02 历史压缩 | 哪种结构既保关键事实又降低总成本 | MemOps 长短对照 + 人工条件题 | 源区间、模型、输入/输出预算 |
| 3 | EXP-03 检索与融合 | 哪条路提高证据进入最终输入的概率 | MemOps 长历史；后续 LongMemEval | 同一记忆表示、chunk、预算、答案模型 |
| 4 | EXP-04 输入构建与预算 | 候选相同时，如何分配输入和排列内容 | 固定已缓存候选 + 任务探针 | 候选集合、状态、模型 |
| 5 | EXP-05 TP 的价值 | 主题目录是否比额外复杂度更有收益 | 多主题/跨时间轨迹 | 其余模块、可见前缀、调度方式 |
| 6 | EXP-06 长期偏好与范围 | 如何区分长期、临时、假设、他人信息 | PersonaMem-v2 审计子集 | 人物分组、更新接口、评分规则 |
| 7 | EXP-07 更新器后训练 | 训练是否改善连续状态维护和后续选择 | 经审计的 MemOps 训练/验证/测试组 | 同一基础模型及未训练基线 |
| 8 | EXP-08 遗忘与反思 | 不再使用、替换、反思与删除如何分开 | 人工语义集，之后审计其他标签 | 数据删除机制不变 |
| 9 | EXP-09 多步行动 | 记忆是否改善后续工具/环境决策 | MemoryArena 或确定性测试环境 | Agent、工具、环境、任务版本 |
| 10 | EXP-10 性能与调度 | 如何减少等待与费用，是否需要新基础设施 | 固定回放与故障注入 | 算法策略、请求负载、配额 |
| 11 | EXP-11 真实产品反馈 | 记忆是否改善真实体验而非只答对合成题 | 明确许可的真实反馈 | 展示候选、排序、反馈选择机制 |
| 12 | EXP-12 更复杂任务组织 | 完整 TP、自动任务完成、多 Agent 是否必要 | 已有失败案例驱动的新测试 | 安全边界、主体/任务归属 |

顺序是依赖建议，不要求每项都实现。先围绕最常见且可证实的失败做实验，不因名字新就增加模块。

## 4. EXP-01：记忆更新器

### 问题与假设

明确纠正、条件变化、未来计划、他人信息和临时约束容易产生不同类型的错误。要分别看“模型给了什么建议”和“提交器保存了什么”。目标是改进有证据支持的更新，而不是把用户画像写得更长。

### 实验组

固定首版提交器，比较：现有提示词；更严格结构化字段说明；显式分开事实/计划/假设；规则处理确定性事件再让模型理解其余内容。先测单步，再测连续。known_field 与 discovery 分开，不让已知目标字段的诊断成绩冒充自动发现能力。

### 指标与诊断

ADD/UPDATE/KEEP 各类准确率、误覆盖、主体/范围错误、证据支持、旧值残留、后续问答和选择、调用成本。只修复 UPDATE 而增加大量错误更新也不是整体改善。检查当前状态错误但答案偶然从最近消息答对的情况。

### 接纳条件

新的策略必须在保留的回归样例上不破坏关键正确性；改善能在独立人物/轨迹中出现，成本可接受。具体阈值在观察基线后预先写入实验配置，不在看到结果后临时调整。

## 5. EXP-02：Episode 压缩

### 保持不变

固定 Raw 区间、可见上限、任务/事实的历史版本、回答模型和检索。所有压缩方案遵守来源、发布和删除规则。不得某组提前读取未来 CTS，另一组只看旧原文。

### 可比较的方法

普通摘要；结构化条目；更细的原子命题；一次结构化调用与分阶段处理；是否允许有限原文回查；是否提供当时 CTS；不同压缩触发水位和条目粒度。默认核心采用非递归 Raw-based Episode；递归摘要作为明确单独的对照，不混为同方法。

### 指标

条件/否定/数字/主体保留，事实变更顺序，证据有效性，后续证据命中，最终任务表现，以及压缩本身、修复、回查与回答的总调用成本。文本更短不等于更好；若多次压缩调用比省下的主输入更贵，需要如实报告。

### 实验陷阱

摘要与原文条目重复可能增加召回排名而非增加信息；应按规范化来源统计覆盖。更长的输出也可能自然占用更多预算，至少报告固定输出预算和成本受控两种条件。七项处理职责不等于一定要七次模型调用。

## 6. EXP-03：检索与融合

第一步比较 BM25、语义、固定 RRF；输入相同的记忆和 chunk，记录各路候选及最终输入。第二步才增加 reranker、查询改写、时间/重要性信号、Graph 或模型权重调节。

每新增信号，要写明它解决的失败：精确错误码、别名、跨事件联系、旧值干扰、任务范围错配等。Graph 需要可靠的实体/关系来源与版本，不是把原有事实随便连线。时间新近不自动等于当前有效，importance 分数也不是事实真实性。

测量证据进入候选和进入最终输入两层指标；固定候选池后才研究重排，避免把召回提升和重排提升混在一起。不同 embedding 模型/维度重建索引，不能共用不兼容向量。

模型动态调权会新增调用与随机性，必须计入费用。只有在固定双路有明确弱项且新策略在独立样例上改善，才考虑升为默认。

## 7. EXP-04：Context Builder 与预算

先缓存同一批候选、状态和原文，让不同构建器决定选择和顺序。比较：固定四层配额与动态配额；保留更多 Recent 或更多历史；是否把当前有效约束放在更容易读取的位置；同源去重规则；需要时进一步回查。

请求总预算始终包括工具定义、输出 schema、协议开销、输出预留和安全余量。不能让一个策略使用更大实际窗口却只比较 token 比例。上下文全量对照仅在原文确实放得下的子集上进行，不能给它无限预算。

指标包括答案/行动正确性、当前约束遵从、证据在输入中的覆盖、预算失败、生成延迟和费用。固定候选但模型表现不同说明输入构建值得研究；不因此断言可以从日志读取模型内部注意力。

## 8. EXP-05：TP 是否值得保留

### 首先做 C 与 D

C 不运行 TP；D 在自己的 Namespace 中按可见前缀生成轻量主题条目。二者其余配置相同。D 不能提前看完整轨迹做离线主题总结。调度采用相同确定性屏障或分别报告真实异步延迟。

### 再比较的方向

预设主题与动态主题；只检索条目与先目录后展开；主题介绍长度；增量批次；匹配阈值；不同重复来源去重。完整任务快照型 TP 作为另一种独立策略，不能无记录地替换轻量 TP 后仍使用相同策略名。

### 必须回答

TP 帮助了哪类跨时间/多主题问题？是否只是多给了输入预算？后台费用、等待以外的资源占用和错误归类增加了多少？失败是否源于主题归错、介绍过时、条目没命中或最终未使用？

如果收益很小或只在少数场景出现，可以按任务开启，不必坚持所有推荐、所有交易都生成 TP。没有收益也是有效结论。

## 9. EXP-06：长期偏好、临时意图与跨会话

首版只处理明确可长期保留的信息。后续在审计 PersonaMem-v2 等材料之后，研究含蓄表达、偏好变化、指代主体和适用范围。

对每次推断同时保存行为事实/表达、证据、模型假设及确认状态。一次点击、下单、忽略或一次抱怨，不自动成为永久偏好。只知道用户做过某事，也不等于知道为什么做。

以人物/背景分组划分。完整人物档案可供核对标签，不能放进当时 Agent 输入。known_field 与自主发现、显式表达与含蓄推断、用户本人和代他人询问分别报告。

可研究置信度校准、是否值得追问、什么时候仅保存观察。只有在有明确标签定义和足够样本时才解释某个 confidence 数值的统计意义。跨领域迁移需要单独授权/产品语义，不把一个领域的全部记忆自动暴露给另一个领域。

## 10. EXP-07：后训练更新器

### 进入条件

取得许可明确、经过审计的数据；固定三类更新接口与证据格式；拥有未见测试组；能够单步与连续评测；选定实际可训练的模型及资源环境。首版调用的聊天 API 不代表那个服务模型可训练。

### 公平比较

必须先运行所选可训练基础模型的未训练基线，再与同基础模型的训练后版本比较。若首版用某个商业 API，而训练选另一个开源模型，不能把两者差异全部归因于训练。固定检索、压缩、预算、提交器和后续回答模型。

先训练记忆操作判断，不同时训练更新器、摘要器与最终回答模型；否则无法定位效果来源。量化、推理参数、提示词和模型版本变化要分别记录。

### 起步流程

先用少量合格样例验证加载、前向、训练、保存、重新加载和结构化推理；记录内存/时间/失败，再扩大规模。不承诺某台机器一定可以训练某个规模。SFT 与 LoRA 是可测试方向，具体实现和许可依选定模型确认。

训练输入只包含触发时刻已知材料，输出含操作、目标、值与证据，不把完整人物背景和未来助手确认当先验。生成格式合法不代表语义正确；训练后仍通过原提交器校验。

### 结果

单步进步是否在连续回放中保留？误覆盖是否增加？后续选择是否改善？不同来源是否泛化？延迟/成本如何变化？LongMemEval 等保留的外部测试不进入训练或提示词反复调试。

## 11. EXP-08：遗忘、反思与数据删除

四种语义分开：旧事实被新事实替代；用户不希望再主动提起某事；用户要求删除相应数据；模型基于旧材料形成新的解释或假设。首版的数据删除是必须有的工程能力，不等待这项研究。

MemOps 的 Forget/Reflect 等标签只有在逐项审计含义之后再映射。反思生成的解释应保留支持/反对证据及假设身份，不能变成无来源的确定用户事实。删除权不能由模型置信度覆盖。

可比较的指标：不该使用的信息是否仍出现、误删/误压制、删除后重建能否排除旧来源、反思是否得到新证据支持及是否损害后续任务。外部服务/备份的实际保留范围单独记录，不宣称本地删除能撤回已经发送的请求。

## 12. EXP-09：记忆与多步行动

在 Agent 已能稳定记录模型输入、工具动作和反馈后，再接一种多阶段环境。MemoryArena 的角色沿用数据源计划，实际版本和环境可用性在接入时验证；不把其环境安装作为第一轮本机微调前置条件。

固定基础 Agent、环境版本、工具、评分、任务初始化和随机种子（若支持），只替换记忆方法。外部观察和动作顺序必须保存，记忆只能用已经发生的反馈。测试中途重启时避免重复产生真实副作用；优先使用可重置的模拟环境。

同时报告成功率、约束违反、重复动作、尝试次数、成本和故障。比记忆问答更好不必然等于用户更满意，多步任务成功也不等于适合真实交易。

## 13. EXP-10：性能、资源与多实例

先测哪里慢：接收排队、更新、压缩交接、检索、主生成、TP、embedding。模型/API 延迟和应用吞吐分别测。用模型桩测试队列和事务，用真实小规模调用测端到端，结果分开。

可按证据依次研究：缓存和增量索引；前后台配额；更合理批处理；减少不必要更新调用；后台优先级；增加 worker；迁移 RabbitMQ 等消息系统；多实例执行。不得因为换了队列就删掉现有幂等、epoch、去重和恢复规则。

故障测试覆盖进程崩溃、数据库临时不可用、模型超时、索引不可用、重试风暴、删除与发布竞争。优化只有在不丢消息、不重复提交、不越权读取、预算可控的前提下才能接纳。

高可用需要明确恢复点、可接受丢失范围、恢复时间和实际演练；第一版通过重启恢复不等于已经实现集群高可用。

## 14. EXP-11：真实产品反馈

首个领域、目标用户和具体决策场景仍需选择，不同时默认建设两个完整产品。数据采集必须经用户许可，保存展示候选、排序、当时约束、选择/拒绝、表达理由与后续体验；允许用户纠正和删除。

研究结论分层：是否维护正确记忆；是否遵守已知约束；是否改进任务结果；是否改善真实体验。点击/下单只能证明行为发生，不能单独证明长期偏好或满意。用户只对展示内容做反应，不能把未展示的候选当成用户拒绝。

真实产品研究应先做描述性错误分析和小规模受控比较，再讨论训练偏好或离线策略估计。采样方式、选择机制、缺失反馈、反复使用的用户分组都要记录，不能把合成题成绩直接变成商业效果宣传。

## 15. EXP-12：完整 TP、自动任务结束和多 Agent

只有现有失败案例说明有必要时再引入。完整 TP 可以组织任务阶段、决策和完成快照，但它与轻量主题目录是不同对象，应独立 schema/配置/基线。自动任务完成需要“完成”的标签和可检验证据，不能只是训练模型更频繁说完成。

多 Agent 共享可写记忆会增加权限、冲突、提交顺序和来源归属问题。先明确谁有权提出、谁有权提交、冲突如何解决；保留单写者或显式并发协议。不要直接让多个后台模型同时覆写一份用户画像文件。

Recent Compressed 等历史候选不重新进入默认结构；确有失败案例时作为独立实验实现，报告额外表示是否带来重复、过时和预算浪费。

## 18. 来源与结论边界

本文件的研究方向来自用户本轮认可的完整方案及已经提供的数据源/产品文件；具体实验拆分、固定项和验收规则为本次新增建议。没有重新取得仓库最新的原同名文件，不声称这是已核对所有旧条目的完整 diff。

外部方法名用于标识可能的比较方向，不在没有重新验证来源和运行数据时引用“最新最好”或性能提升。实现时可以沿用原产品文件中的官方资料入口，但论文/框架的结果不自动验证本项目组合。
