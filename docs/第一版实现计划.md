# 第一版实现计划

记录日期：2026-10-12。来源：本次对话中助手提出的分阶段计划，按用户要求保存到仓库。状态：实施建议，尚未执行或验证。

先把主要模块做成能运行的简单版本，第一版完成后，再逐个模块开展实验、训练和优化。模型训练放在后续的[第一版后深入研究计划](./第一版后深入研究计划.md)中，以第一版作为比较基线。

## 1. 第一版的目标与范围

给系统一段持续进行的对话，它能够：

1. 保存完整的原始内容。
2. 记住目前有效的信息，以及当前任务进展。
3. 在历史变长后，整理和查找过去的内容。
4. 用户修改信息后，在后续回答中使用更新后的信息。
5. 出错时，让我们查清楚错误发生在哪里。

第一版可以先用简单脚本运行，在一个隔离的测试空间里把流程跑通。现成模型通过提示词完成整理和更新，先建立可运行、可比较的基础版本。

这里的测试范围是实现顺序上的简化。新产品的用户、会话与长期记忆归属仍按[产品方向与技术选型](../../docs/产品方向与技术选型.md)继续讨论，不把旧研究中的 DSH 或单 session 范围作为新产品定案。TP 在本实验框架中保留简单可开关版本，不表示每次推荐或交易都必须生成 TP。

## 2. 阶段一：先让系统能记录信息、更新记忆

### 第 1 步：准备少量测试对话，明确系统应该怎么表现

**为什么先做这一步？**

后面每做一个模块，都需要有具体例子判断它是否工作正常。

**具体做什么？**

先准备大约 10 条小样例，覆盖几种基本情况。以下均为构造的测试例子：

- **新增信息**：“我现在住在杭州。”
- **修改信息**：“我已经搬到上海了。”
- **尚未发生的变化**：“如果拿到那个 offer，我可能搬去上海。”
- **继续任务**：“接着帮我安排刚才说的周末活动。”

给每条样例写清楚：

- 哪些信息应该被记住？
- 哪些信息应该更新或保持？
- 后面再问时，应该怎样回答或继续任务？

这些可以先手工编写，作为功能验收样例；之后再从选定的数据集中补充。功能验收样例与后续训练、正式评测数据分别管理。

**完成标志：** 有一小组“输入对话 + 预期行为”，后面所有步骤都可以用它检查。

### 第 2 步：跑通基本对话，保存完整原始记录

这里对应 **Raw：完整原始记录**。

**为什么做？**

后面的记忆、摘要和任务状态都需要有出处。出了问题，也要能回到原始对话检查。

**具体做什么？**

先实现最简单的流程：

1. 输入一条消息。
2. 调用现成模型。
3. 显示回答。
4. 保存用户消息、模型回答和发生顺序。

如果有工具调用，也保存工具的实际返回结果。

**完成标志：** 可以持续对话，关闭程序后重新打开，仍然能读取之前的完整记录。

### 第 3 步：维护当前信息和当前任务状态

这一步区分两类内容：

| 内容 | 例子 | 用途 |
| --- | --- | --- |
| 当前有效的信息 | 用户现在住上海，这次活动预算是 300 元 | 为后续回答和选择提供依据 |
| 当前任务状态（CTS） | 正在安排周末活动，还缺具体日期，下一步需要询问 | 帮助系统继续推进任务 |

**为什么做？**

原始对话记录的是整个过程。继续工作时，系统还需要知道“现在是什么情况”。

**具体做什么？**

每次收到新消息，让现成模型按照固定格式整理：

- 有什么新信息需要保存？
- 哪条已有信息需要更新？
- 哪些信息应该保持？
- 当前任务有什么进展，下一步是什么？

第一版通过提示词完成这些判断。程序保存结果，并保留信息的原文出处和旧记录。涉及下一次回答的信息更新，应在该次模型调用前生效。

当前有效信息沿用已有设计中的事实身份、版本和来源关系整理；CTS 维护任务进度，并引用相关信息。具体字段和接口在实现这一步时展开。

**完成标志：** 用户明确纠正信息后，当前记录能够变化；任务进展也能单独更新。例如，“用户搬家了”不会被当成“活动安排已经完成”。

## 3. 阶段二：让对话变长之后，历史仍然能被使用

### 第 4 步：加入分段摘要 Episode

**为什么做？**

对话越来越长时，每次都把全部原文交给模型，成本和输入长度都会增长。需要一种较短的历史阅读材料。

**具体做什么？**

先采用简单规则：

- 历史积累到固定长度，就整理较早的一段连续原文。
- 从这段 Raw 生成摘要。
- 摘要保留原文出处。
- 原始记录继续保存。

第一版先用固定切分规则。何时切分更合适、怎样减少摘要失真，放到后续研究。固定边界的一段内容处理完成并成功保存后，再将相应摘要用于后续上下文。

**完成标志：** 一段较长对话能够变成较短的摘要；看到摘要中的某个信息时，可以查回原文。

### 第 5 步：加入历史查找和上下文组装

这里包含两个职责：

- **检索：找到可能相关的历史材料。**
- **Context Builder：决定这一次实际交给模型哪些内容。**

**为什么做？**

保存了历史之后，还需要在合适的时候把它找出来，并放进模型输入。

**具体做什么？**

先做简单的查找：

- 查找相同关键词，例如人名、地点、项目名。
- 查找意思相近的内容。
- 用固定规则合并结果，去除重复，并检查信息的适用范围和版本。

然后按固定顺序组装模型输入：

1. 固定规则。
2. 当前任务状态。
3. 选中的历史信息。
4. 最近几轮对话。

给整个输入设置长度上限，并保存每次模型调用实际使用的内容。具体融合算法、长度配额和字段在实现这一步时确定。

**完成标志：** 即使早期原文没有直接放进模型输入，系统也能找到相关记录，并依据目前有效的信息回答。

### 第 6 步：加入简单的主题整理 TP

**为什么做？**

一个主题可能分散在很多段对话中。按时间生成的摘要，需要再补一种按主题查找材料的方式。

**具体做什么？**

先预设少量主题，例如“居住信息”“出行计划”。

- 为主题保存一句简单介绍。
- 从原始记录中，为相关主题追加简短条目。
- 每条都保留原文出处。
- 后续出现同一主题的新内容，继续追加。
- 需要时，可以按主题查找这些材料。

TP 从 Raw 整理，保持与 Episode 的独立来源关系；它组织主题材料，当前任务进度仍由 CTS 维护。TP 的生成不作为对话继续或 Episode 发布的等待条件。

把 TP 做成可以开关的模块，方便后面比较它是否有帮助。

**完成标志：** 不同时间出现的同一主题内容，能够集中找到，并且仍能追溯到原文。

## 4. 阶段三：把整个系统接起来，形成基础版本

### 第 7 步：连续运行测试对话，检查整个流程

**为什么做？**

单个模块能运行，还需要确认它们接起来以后，信息能正确传递。

**具体做什么？**

连续运行第 1 步准备的样例，重点检查：

- 新信息有没有保存？
- 用户纠正后，后续回答是否仍然使用旧信息？
- “可能发生”有没有被误当成“已经发生”？
- 历史经过摘要后，关键内容还能不能找到？
- 当前任务能否继续推进？
- 回答出错时，能否查到它使用了哪些记忆和原文？

同时保存每一步的处理结果，以及调用次数、输入长度等基本记录。连续运行时使用系统自己更新出的记忆，以便观察前一步错误对后续的影响。

**完成标志：** 得到三个东西：

| 交付内容 | 用途 |
| --- | --- |
| 能够连续运行的基础系统 | 演示整套上下文保存和使用流程 |
| 固定测试的运行结果 | 作为后续优化的比较对象 |
| 错误记录 | 告诉我们下一步应该研究哪个模块 |

至此，第一版完成。它包含主要模块的简单实现；运行结果和已知错误是后续研究的起点，尚不能据此宣称真实用户效果已得到验证。
