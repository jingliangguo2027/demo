## 1. 首版目标与最终产物

首版要让开发者能够完成以下完整过程：打开网页聊天；观察当前事实与任务状态如何变化；让历史经过压缩和主题整理；查看本次检索和真实模型输入；载入固定数据并重复运行；比较不同策略；从失败回答追溯到错误发生的模块。

最终交付包括：

1. **一个 Web 研究应用。** 有聊天、记忆、实验、配置四个工作区；支持逐轮检查，不要求精美的商业化界面。
2. **一个可复用的上下文核心。** 在线聊天和离线回放调用相同的更新、检索、构建、发布逻辑，不维护两套算法。
3. **四组真实可运行的对照配置。** 最近消息窗口、普通滚动摘要、核心方案、核心方案加 TP。
4. **首批数据与结果。** 至少 10 条人工完整轨迹，20—30 条经审计的 MemOps 完整轨迹，运行清单、逐项结果、成本和失败记录。没有许可时不打包上游原始数据。
5. **开发和复现材料。** 数据库迁移、OpenAPI、固定配置、提示词版本、自动测试、部署说明及一条可执行的实验命令。

这里的“完整”指闭环和关键正确性完整，不指所有研究设想均已验证，也不指一个同时完成吃喝玩乐与找房业务的通用产品。首版用通用测试场景承载研究；两个领域的正式产品仍分别规划。

## 2. 范围：必须做、简单实现、明确后置

### 2.1 必须形成实际行为

| 模块 | 首版要求 | 不算完成的情况 |
| --- | --- | --- |
| Raw | 消息、工具事件、来源和顺序持久保存，可重启读取 | 只留控制台日志 |
| 当前事实 | 新增、更新、保持；当前视图和历史版本；证据可回查 | 只有无结构的用户画像摘要 |
| CTS | 目标、进展、未解决项、下一步；切换、暂停、恢复 | 每轮重写一段摘要，无法定位任务 |
| Episode | 从固定 Raw 区间生成结构化片段，校验后原子发布 | 只有提示词，没有作业与交接协议 |
| TP | 轻量主题目录、介绍、原文引用、分条材料；可开关 | 只留空接口或把任务完成摘要改个名字 |
| 检索 | BM25、语义、固定融合；Raw 可直接查找 | 只能查摘要，找不到被遗漏的原文 |
| Context Builder | 四层输入、预算、版本过滤、工具消息合法性、输入快照 | 只展示检索结果，不知道实际发送内容 |
| 运行记录 | 候选操作、实际提交、检索候选、最终输入分别记录 | 只记助手回答和 token 总数 |
| 数据回放 | 事件流与评分标签隔离；单步诊断和连续运行 | 每步注入标准记忆，却宣称连续运行 |
| 实验隔离 | 每个实验使用独立可变记忆、索引和作业 | 两种方法复用一个正在变化的数据库视图 |
| 生命周期 | 幂等、恢复、删除屏障、有限重试 | 重启后丢任务，或删除后后台写回 |

### 2.2 首版先做简单版本

关键词采用一个明确的 BM25 实现；中文分词采用固定版本的分词器并保留错误码、数字、英文标识符。语义采用一个固定 embedding 模型。融合采用固定 RRF。Episode 采用一次结构化模型调用加程序校验，必要时有限修复。TP 使用预设主题和轻量匹配；只追加条目，介绍允许生成新版本。跨会话仅使用用户明确声明、允许长期保留的信息，不自动把一次行为推断为永久偏好。

“可开关”表示已经实现且能运行，关闭时有明确的数据和成本行为，不是尚未开发。

### 2.3 不作为首版完成条件

Graph 检索，时间/重要性五路加权，模型动态调节检索权重，完整任务完成快照型 TP，Recent Compressed 中间层，自动学习任务完成阈值，多 Agent 共享可写记忆，模型微调，大规模集群，高可用故障切换，真实商户/房源业务接入，未经确认的主动推荐策略。

这些内容统一进入配套后续研究计划。数据归属、来源记录、版本不倒退、标签隔离和删除屏障不允许作为“省成本开关”关闭。

## 3. 术语与首版决策

### 3.1 术语

| 术语 | 本项目中的准确含义 |
| --- | --- |
| Raw | 被接纳进入运行顺序的原始事件；原文不因摘要而删除 |
| Ingress | 已经持久接收、尚未被运行器接纳的输入；用于处理生成期间的新消息 |
| Fact | 带主体、字段、值、范围、条件、有效时间和出处的信息版本 |
| CTS | Current Task State，某个任务当前的业务状态，不是框架执行检查点 |
| Episode | 固定连续 Raw 区间的一次结构化历史整理；默认不递归压缩旧摘要 |
| TP | 轻量主题材料目录：主题介绍、分条材料与原文引用 |
| Namespace | 可变记忆的隔离空间；是权限与实验隔离的基本边界 |
| Run | 一次实验或在线执行记录；实验 Run 绑定独立 Namespace |
| Turn | 一次被接纳的用户输入及其后续模型/工具执行 |
| Call | 一次实际模型请求，包括更新、回答、摘要、TP、评分等用途 |
| Snapshot | 某次模型调用前冻结的真实请求与所依赖的状态版本 |
| visible_through_seq | 本次处理允许读取的最高 Raw 顺序号，不是时间戳 |
| generation_epoch | Namespace 的生命周期代次；删除或重置时递增，使迟到写入失效 |

### 3.2 工程决策表

下面属于本次首版默认决策；修改必须增加配置版本或设计变更记录。

| ID | 决策 | 原因与边界 |
| --- | --- | --- |
| D01 | Vue 3 + TypeScript 前端；Spring Boot 应用入口；Python + FastAPI 运行服务 | 延续产品技术倾向；上下文算法只在 Python 实现 |
| D02 | PostgreSQL 持久存储，pgvector 保存语义索引；BM25 索引可重建 | 不把普通数据库全文检索直接叫 BM25 |
| D03 | 首版使用数据库作业表和独立 worker，不强制 Redis/RabbitMQ | 先验证持久队列、租约、幂等；不删掉未来迁移空间 |
| D04 | LangGraph 仅负责流程节点与执行检查点 | 事实、CTS、实验快照仍由项目负责 |
| D05 | 每个 Namespace 同时最多一个前台执行者 | 先用串行写入降低并发歧义，不承诺单用户多任务并行生成 |
| D06 | 用户输入先持久进入 Ingress，再按接纳顺序进入 Raw | 当前回答生成时可接收新输入，但不污染已冻结请求 |
| D07 | 当前事实与 CTS 在下次相关主模型调用前提交 | Episode/TP 的延迟不得导致新要求失效 |
| D08 | Episode 在安全边界发布；TP 不阻塞主调用 | 两类后台工作的等待语义不同 |
| D09 | 默认四层逻辑布局为 Rules → CTS → History → Recent Raw | 不新增第五层用户画像；事实通过 CTS 约束/History 呈现 |
| D10 | 所有派生内容带来源；后台摘要不得写当前事实表 | 避免旧摘要把新事实覆盖回去 |
| D11 | 一次实验一个独立 Namespace | 原始只读数据可共享，可变记忆不能共享 |
| D12 | 首版原始工具执行只提供只读、固定测试工具 | 不默认允许支付、邮件发送、任意 shell 或外部写入 |
| D13 | 在线用户记忆按用户和领域隔离；长期记忆需明确范围 | 不把吃喝玩乐偏好自动搬到找房任务 |
| D14 | 模型、价目、上下文上限在接入时核实并固定配置 | 不在计划中声称某 API 永久便宜或某别名永不变化 |
| D15 | 20—30 条 MemOps 先作为审计/调试批次 | 不把小规模诊断包装成泛化结论 |

## 4. 系统结构与职责

### 4.1 部署结构

```text
浏览器 Vue
  └─ Spring Boot：鉴权、页面 API、SSE 代理、配置/实验入口
       └─ Python API / 运行服务
            ├─ context_core：事件、事实、CTS、检索、构建
            ├─ agent_runner：主模型与只读工具循环
            ├─ experiment_runner：固定数据与对照运行
            ├─ background_worker：Episode / TP / embedding / 导出
            └─ PostgreSQL + pgvector + 本地持久对象目录
```

在线输入和数据集输入都经 `EventAdmissionService` 进入同一核心。线上不调用一套“优化版记忆”，测试却调用另一套简化函数。测试允许替换外部模型/工具为确定性桩，但必须保留核心事务和可见性检查。

首版只暴露 Spring Boot 端口；Python 和数据库仅供内部网络访问。浏览器不得拿到模型密钥。用户标识、Namespace 权限由后端鉴权结果确定，不信任浏览器随意传入的 `owner_id`。

### 4.2 数据写入所有权

| 组件 | 可以写什么 | 不得写什么 |
| --- | --- | --- |
| Spring Boot | 应用用户、访问权限、入口配置；通过内部 API 发起操作 | 不直接修改 facts/CTS/episode/checkpoint |
| 事件服务 | Ingress、Raw、Turn、顺序与幂等记录 | 不跳过记忆更新校验 |
| Memory Committer | 事实版本、操作结果、任务/CTS、投影进度 | 不改历史 Raw 原文 |
| Episode worker | Episode 版本、发布记录、压缩覆盖游标 | 不提交当前事实/CTS |
| TP worker | 主题介绍版本、条目、处理游标 | 不改变任务完成状态 |
| Index worker | 派生索引及构建版本 | 不改变源记录含义 |
| Evaluator | 标签库读取、评分、审查记录 | 不把标签写入被测 Agent 的 Namespace |

数据库可共实例，但应用表、运行表、评分标签采用不同 schema/连接权限。Python Agent 进程的凭据不能查询评分标签表。

## 5. 四个前端工作区的交付要求

### 5.1 对话工作区

左侧会话/任务导航，中间对话，右侧当前 Turn 检查器。用户可发送、取消当前执行、切换任务、明确纠正某条记忆。每个消息显示已接收、排队、运行、完成、中断或失败状态。断网恢复后，显示既有执行结果而不是自动再发一次请求。

检查器固定包含：原始输入；更新前事实/CTS；模型候选操作；提交/拒绝结果；检索请求；候选及各路排名；最终选入/排除原因；真实请求分层视图；原始供应商请求体（脱密钥）；调用耗时、用量、错误及重试。普通聊天页默认折叠这些信息。

### 5.2 记忆工作区

提供 Raw、事实、CTS、Episode、TP、附件六个标签页；支持当前/历史视图和来源跳转。事实列表至少显示主体、字段、值、范围、状态、条件、版本、来源。不要把 `confidence` 画成已经校准的准确概率。

用户的“纠正”通过新增控制事件和规范提交生成新版本，不允许前端直接改表。`pin/unpin` 是显式用户控制事件；Pin 不提高内容指令优先级，也不能跨 Namespace。

### 5.3 实验工作区

数据源 → 轨迹 → 运行 → 轮次四级浏览；创建运行时冻结配置；可单步前进、连续运行、暂停、取消、从检查点分支。显示结果的分母、失败/跳过/未评分数量，避免只展示通过案例。

并排比较至少支持：答案、当前事实 diff、CTS diff、召回来源、最终输入、成本和失败分类。实验详情页可显示 gold；这些接口不对 Agent 暴露。

### 5.4 配置工作区

模型职责分开配置：回答、更新、Episode、TP、embedding、可选评分。首版允许前四项共用一个已验证的 API 模型。配置保存为新版本，不覆盖已运行实验。新增配置先通过格式、供应商能力和预算验证，再允许选择。

真实密钥只能在后端环境变量/秘密存储设置；页面仅显示已配置/未配置/验证失败与末尾脱敏标识，不提供回显密钥的接口。

## 6. 归属、顺序与可见性模型

### 6.1 Namespace、Run、Session、Task 的关系

- `owner_id`：真实登录用户/本地开发账户。真实身份只存在应用层。
- `subject_id`：记忆主体。线上通常为当前用户；实验中为脱敏的虚构人物标识。它不同于事实中的“用户的朋友”等被描述主体。
- `domain_id`：研究通用域或某个产品领域；跨领域默认不读取。
- `namespace_id`：上述主体的一份可变记忆空间。实验每个 Run 新建；线上同用户同领域可以跨 Session 复用。
- `run_id`：实验必须有且配置不可变；在线可为空，由每次 Call 保存实际配置版本。不要为了在线换模型配置而不经用户说明复制/丢弃长期记忆。
- `session_id`：一次会话入口。可有多个任务，也可以显式恢复已有任务。
- `task_id`：任务跨会话恢复时保持不变。恢复必须验证它属于当前 Namespace。

数据库查询必须在 SQL/索引候选生成阶段约束 `namespace_id`、领域和可见范围；不能先跨用户检索，再让模型“自己忽略”。用户长期记忆读取仍受 Namespace 限制。实验人物 A、实验人物 B、真实用户的记录不互通。

### 6.2 两段式接收：先不丢消息，再确定处理顺序

第一版采用持久 Ingress + Namespace 串行运行器：

1. 收到 HTTP 输入后，在事务中按幂等键写入 `inbox_messages`；原始内容立即持久保存。返回 `202` 和 `ingress_id`。
2. 当前模型调用可以完成；其输入快照不会被新输入修改。UI 将新输入显示为“已保存，等待接纳”。
3. 在下一次模型调用或工具执行前检查 Ingress。若有新用户输入，当前 Turn 不再执行尚未执行的工具调用，标记 `interrupted_by_new_input`，然后按接收顺序接纳下一条输入。
4. 接纳时，在一个事务中分配 Namespace 单调递增的 `event_seq`、写入 Raw、创建新 Turn、将 Ingress 标为 `admitted`。`ingress_id` 只能映射一个 Raw 事件。
5. 下一条消息完成事实/CTS 处理后才进入新的回答调用。已经接收的后续消息仍排队，不能提前进入当前 Turn。连续多条输入时，每条都先处理状态；被更新输入取代的旧 Turn 可以不再生成独立答案，但必须标为 interrupted，而不是显示成丢失或成功回答。

`received_at` 是用户输入抵达服务器的时间；`event_seq` 是核心实际接纳顺序；`occurred_at` 是原数据提供的业务时间。三者不得混用。当前生成的答案可能先完成，再接纳用户的新要求；UI 必须标明它依据哪一轮输入产生，不能把旧答案挂到新消息下面。

这样可以同时满足：新输入立即留存；当前请求保持固定；下次相关回答处理新要求；工具副作用不越过中断边界。首版不要求强制抢占供应商已经执行中的请求，也不声称取消会撤销其费用。

### 6.3 可见性

每个更新调用、摘要作业、检索请求和主模型调用都携带 `visible_through_seq`。任何可读取的 Raw 事件必须属于该 Namespace 且 `event_seq <= visible_through_seq`。派生记录还必须满足其所有证据均在可见范围内。

Episode 作业另存触发时的 `base_state_revision` 或历史状态快照引用；不能在执行时读取“最新 CTS”来解释更早的历史。TP 的每次增量也冻结上限。原始数据集不得一次性以普通可检索 Raw 的形式导入未来全部内容：先放只读数据仓库，回放到某条时才接纳到 Agent Namespace。

检索时间戳过滤不能代替顺序号检查。时间缺失、相同时间或回填时间，都不允许突破事件可见范围。

## 7. 数据结构与持久化契约

### 7.1 公共约定

ID 用 UUID 字符串或同等无歧义标识；时间用带时区的 ISO 8601，数据库保存 UTC，页面按用户时区展示。金额保存数值与币种，不能只存模糊字符串。JSON 对象必须有 `schema_version`。数据库保存原始文本和结构化值；原始正文不因规范化而丢失。

事件引用使用 `event_id` 和可选正文区间 `[char_start, char_end)`；字符偏移以解码后的 Unicode code point 为单位，不用 UTF-8 字节偏移或 JavaScript UTF-16 下标。跨语言实现应提供转换工具，并用中文/emoji 测试。保存引用原文的哈希；校验区间存在且确实对应原文。

表中 `jsonb` 可先承担扩展字段，稳定的权限、ID、顺序、状态和版本必须有独立列及索引。以下是最低契约，不要求每张表都建立独立服务。

### 7.3 原始事件类型

首版最低类型：`user_message`、`assistant_message`、`tool_call`、`tool_result`、`task_control`、`memory_correction`、`pin_change`。供应商 token 分片、重试、后台租约写入运行日志，不进入对话 Raw。

`assistant_message` 区分完整输出、部分输出和中断输出。工具调用参数及结果必须保存关联 ID。数据集中的历史助手消息标记 `provenance=dataset_history`，不是本系统新生成的回答，也不是用户事实的独立权威来源。

### 7.4 事实变更请求例子

下面是规范化示例，不是 MemOps 原始字段，也不是模型实测输出。

```json
{
  "schema_version": "1.0",
  "namespace_id": "ns_demo",
  "visible_through_seq": 12,
  "expected_state_revision": 7,
  "operations": [
    {
      "action": "UPDATE",
      "subject_ref": "self",
      "predicate": "activity.budget",
      "scope": {"type": "task", "id": "task_weekend"},
      "expected_version_id": "fv_old",
      "value": {"amount": 300, "currency": "CNY"},
      "confirmation": "explicit",
      "source_refs": [{"event_id": "evt_12"}],
      "evidence_note": "用户明确把本次预算从500元改成300元。"
    }

```

模型只产生 `operations/observations/cts_patch` 的候选。`namespace_id`、可见范围、版本检查上下文由服务端注入并校验，不能由模型决定。`evidence_note` 是简短的可审查证据说明，不要求输出模型私有思维过程。

### 7.5 事务与唯一性

一个更新批次事务至少完成：验证 Namespace 存活/epoch；锁定 head；检查 expected_revision；校验所有来源；追加事实版本；更新 head；追加 CTS 版本；记录操作；推进投影进度。格式正确但业务上不成立的候选逐项记录为拒绝；SQL/版本冲突导致整批事务回滚，不形成半个事实更新。

版本冲突时重新读取当前状态，重新生成或规则化重新判断；不得只把 `expected_revision` 改成最新值后强行重放原建议。对同一 `(namespace_id, source_batch_hash, strategy_version)` 的已经提交结果返回原提交。

## 8. 当前事实与 CTS 的更新规则

### 8.1 三种首轮操作

| 操作 | 条件 | 提交结果 |
| --- | --- | --- |
| ADD | 同主体/字段/范围没有已确认当前值，原文明确信息已成立 | 创建版本与当前指针 |
| UPDATE | 明确替代已有当前值；目标和旧版本匹配；不是尚未生效计划 | 创建新版本，旧版可追溯，移动当前指针 |
| KEEP | 没有足够证据替代，或变化仍是条件性/计划性 | 保持当前指针，记录判断和证据 |

`KEEP` 不表示整条消息毫无可记内容。比如“下个月可能搬上海”应保持当前所在地；可另存 plan 观察，但不能把计划当作已经发生的所在地。未标注信息不是负标签；相关训练和评分边界见数据源文件。

### 8.2 主体、范围、时效与证据

- 主体区分自己、朋友、家人、机构。提到别人不更新自己的同名字段。
- 范围为 `user`、`session`、`task`，其中 user 仍只在同 Namespace/领域生效。
- 临时任务约束只覆盖本次任务的适用视图，不重写用户长期偏好。
- 同一键的明确后续纠正可以替代；不同范围出现冲突，标记待确认，不用一个全局“最新文本胜出”规则解决所有情况。
- `effective_from/until` 表示业务有效时间；`event_seq` 表示何时得知。已知未来计划的到期不自动证明事件发生，除非它本身是已确认的时间生效约定并有明确规则。
- 模型总结、助手附和和未被用户确认的推测不能单独作为用户新事实的证据。工具结果只能证明其可信字段，不自动证明偏好。
- 条件、否定、单位、主体、枚举列表必须保留。解析失败不写空值覆盖旧值。

### 8.3 更新器的输入与输出

输入至少包含：固定任务说明、截至 cutoff 的新增可见事件、相关当前事实及版本、当时 CTS、允许字段/范围定义、输出 schema。首版新增事件过长时允许分块，但每块的中间状态有独立提交记录，不能把未来块当先前证据。

规则负责显式任务控制、工具成功/失败等确定性状态；模型处理语义变化。默认每个需要语义理解的新增事件批次最多一次调用及一次格式修复；失败后标记 `memory_update_failed`。首版在这种情况下不继续依赖可能陈旧的状态生成建议，而是显示可重试错误；将来允许降级必须作为独立策略并记录。

### 8.4 CTS 状态机

```text
created → active ↔ waiting_user
             ↕
           paused → active
active / waiting_user / paused → completed 或 cancelled
```

任务完成需要用户明确确认、结构化业务工具的完成证据，或预先约定且可验证的完成条件。不能仅因模型写了“好的，完成了”就完成任务。已完成任务恢复，首版要求显式 `reopen` 事件并产生版本；取消不能被普通聊天自动撤销。

CTS 至少有：`goal`、`status`、`confirmed_progress`、`open_items`、`next_actions`、`applicable_constraints`、`evidence_refs`、`based_on_seq`。已尝试、已成功、待执行分别表示。建议过某个动作不等于已执行。

切换任务默认暂停旧活动任务，不删除它；不将旧任务临时预算复制为新任务预算。恢复时读取该任务有效约束，再补入同领域的长期信息。首版同 Namespace 一次只执行一个前台 Turn，但可以保存多个暂停任务。

### 8.5 受控跨会话

先实现明确声明：“以后都按这个偏好”“长期保留这条信息”等符合产品约定的输入。单次点击、不喜欢一次推荐或替朋友询问只保存事件/带范围观察，不自动提升为长期用户事实。前端展示长期记忆及来源，并允许纠正和停止使用。

“停止主动使用”“被新事实替换”“删除原始及派生数据”是不同操作。首版删除通过第 18 节执行；不能把 MemOps 的 Forget 标签直接映射为数据库 DELETE。

## 9. 一次在线输入的完整运行流程

### 9.1 主流程

```text
HTTP 输入 → 持久 Ingress → 返回 ingress_id
    ↓ Namespace 执行权可用
接纳 Raw / 创建 Turn / 分配 event_seq
    ↓
规则处理 + 语义更新候选 → 校验 → 事实/CTS/投影游标原子提交
    ↓
检查 Episode 交接；成功发布，或使用明确的超时/失败回退
    ↓
冻结可见上限与状态版本 → 检索 → 四层构建 → 请求快照
    ↓
模型调用 → 持久返回/用量 → 按协议保存助手与工具事件
    ↓
若要继续工具循环：先检查新输入、取消、epoch、预算和迭代上限
    ↓
提交工具结果引起的确定性 CTS 更新 → 重建下次输入
    ↓
Turn 结束 → 按条件提交 Episode/TP/索引作业 → 发布完成事件
```

更新调用、摘要调用也要保存自身实际请求，不只记录主回答。是否调用更新器由策略决定；纯规则控制事件不为“统一流程”而额外花一次模型调用。

### 9.2 伪代码契约

下面描述调用顺序，不是可直接运行的框架 API。

```python
async def process_next(namespace_id: str) -> None:
    async with foreground_lease(namespace_id):
        assert_namespace_active(namespace_id)
        turn = admit_next_ingress_atomically(namespace_id)
        if turn is None:
            return
        try:
            update_state_or_fail(turn)
            for _ in range(config.max_agent_iterations):
                check_cancel_and_epoch(turn)
                if has_new_ingress(namespace_id):
                    interrupt_before_next_external_action(turn)
                    return
                settle_episode_handoff_or_fail(turn)
                snapshot = build_and_freeze_context(turn)
                call = await invoke_and_persist(snapshot)
                append_assistant_events_once(call)
                if not call.tool_requests:
                    finish_turn(turn)
                    return
                for request in call.tool_requests:
                    check_new_input_cancel_epoch_and_budget(turn)
                    result = await execute_readonly_tool_once(request)
                    append_tool_result_once(result)
                update_state_or_fail(turn)
            fail_turn(turn, "AGENT_ITERATION_LIMIT")
        finally:
            persist_terminal_or_resumable_state(turn)
            enqueue_eligible_background_jobs(namespace_id)
```

任何 `finally` 中的入队仍检查 Namespace 活跃与 epoch。旧执行者租约失效后不能继续提交；副作用只有只读工具。若未来加入写工具，必须单独设计审批与供应商幂等，不能套用这段重试逻辑。

### 9.3 同步与后台的边界

“同步”是指该状态必须先于依赖它的下次模型请求生效，不是每个 HTTP 请求都阻塞直到所有工作结束。HTTP 首次返回可先确认接收；前端通过 SSE 看进度。TP、embedding 的后台延迟不阻止用户消息被保存。

当前事实/CTS 失败、必要预算不足、权限失败属于本 Turn 显式失败。不得在页面上显示成功，同时默默使用旧状态完成回答。允许人工重试；重试复用原用户事件，产生新的 attempt 和调用记录。

## 10. Episode：从原文到可发布历史片段

### 10.1 触发与区间选择

首版支持手动触发和 token 水位触发。水位只是一组初始配置，不是已证实的最优参数。选取从 `episode_covered_through_seq + 1` 开始、到某个已完成 Turn 边界 `B` 的连续 Raw；保留最近若干 Turn 不压缩。未闭合的工具协议组不能被区间边界截断。

首版默认不在未结束的 Turn 内部压缩；通过工具外置、有限工具轮数控制体积。单个 Turn 仍超过窗口则明确失败，不假装已支持无限长工具链压缩。

触发作业必须冻结：Namespace/epoch、区间起止、Raw 哈希、触发时状态版本、提示词和模型配置、schema 版本、读取与输出预算。`B` 不超过已经完成状态投影的事件位置。相同源区间与配置只允许一个可发布结果。

### 10.2 七项处理职责

将过滤、分类、原子命题、必要上下文补足、变更/冲突、元数据、去重合并成一次结构化生成，不默认拆成七次 API 调用。输出至少包含：

```json
{
  "schema_version": "1.0",
  "summary": "用户调整了周末活动预算，日期仍待确认。",
  "items": [
    {
      "kind": "constraint_change",
      "subject_ref": "self",
      "statement": "本次活动预算由500元改为300元。",
      "scope": {"type": "task", "id": "task_weekend"},
      "confirmation": "confirmed",
      "condition": null,
      "source_refs": [{"event_id": "evt_12"}],
      "fact_key_id": "fk_budget"
    }
  ],
  "open_questions": ["活动日期尚未确认"],
  "uncertainties": [],
  "source_event_ids": ["evt_10", "evt_11", "evt_12"]
}
```

`source_event_ids` 指本片段所处理的源范围，不表示每条事件都包含有用事实。与之前原文相关的外部证据要另记 `supporting_refs`，其顺序也必须不超过 B；不能偷偷扩大压缩覆盖区间。

### 10.3 回查原文与校验

默认允许最多两次受限原文读取，累计字符/token 有上限。模型必须给出要读取的事件/范围或关键词，不得遍历整个数据库。工具始终强制同 Namespace 与截止位置。

程序检查：JSON schema；引用是否存在；来源是否可见；区间是否完整；枚举/单位格式；明显漏失否定、条件、数字的静态提示。静态规则只是错误检测，不保证摘要语义正确。无法确定的项记为 uncertainty；格式修复最多一次，仍失败则不发布。

主调用中使用 Episode 时，涉及可版本化事实的条目通过 `fact_key_id` 解析当前有效视图。旧叙述可作为历史保留，但不能独立覆盖新事实。

### 10.4 发布事务

生成结果先存 draft；只有以下检查全部通过才能发布：

1. Namespace 仍活跃，job.epoch 与当前代次相同。
2. 源区间/哈希仍匹配，所有引用未删除。
3. 当前 coverage 与作业声明的前置 coverage 相同，避免重叠/跳跃。
4. 输出 schema 与必要校验通过。
5. 在同一事务将 Episode 标为 published、推进 coverage、完成作业、写索引 outbox。

发布只改变“历史已经如何整理”的状态，不改 Raw，不改事实 head，不改 CTS。索引写入可稍后完成，但必须记录索引延迟和对应 manifest；未索引不是“没有这条记录”。

## 11. Episode 交接、失败回退与持久作业

### 11.1 两种后台任务不同等待语义

| 场景 | Episode | TP |
| --- | --- | --- |
| 当前主调用正在执行 | 不改它的输入，让其完成 | 不改它的输入 |
| 下一次主调用前 | 等待所需区间作业到达已发布/失败/超时状态，或按规定回退 | 不等待 |
| 生成失败 | 不推进 coverage；保留原文 | 不推进对应成功游标；主调用继续 |
| 作业迟到 | 检查区间/coverage/epoch，再决定发布或作废 | 检查来源/epoch/条目去重 |

不是每次调用都无条件等待所有历史 Episode；只等待 Context Builder 计划依赖的交接作业。没有待压缩区间则继续。TP 完成不触发 Episode 重新生成。

### 11.2 首版回退规则

Episode 等待达到配置上限，或作业明确失败时：先尝试按**最后已发布 coverage**构建输入，将其后必要的未压缩 Raw 放入预算。能够容纳则标记 `degraded_raw_fallback` 继续，并记录缺失的压缩结果；不能容纳则返回 `COMPACTION_REQUIRED`，允许重试/取消，不静默丢弃最新约束。

回退不推进 coverage，也不把失败 draft 放入检索。迟到 Episode 可以用于未来调用，但不能修改已经保存的 Snapshot。实验报告必须统计回退次数；比较时等待策略和作业调度模式固定。

### 11.3 作业状态机

```text
queued → running → succeeded
              ├→ retry_wait → queued
              ├→ failed
              ├→ cancelled
              └→ obsolete
```

`obsolete` 用于 epoch 失效、来源已删除、区间已被有效发布等情况，不等同于模型生成错误。worker 从持久表领取作业并设置租约，处理期间续租；进程崩溃、租约过期后允许其他 worker 接手。调用外部模型可能重复收费，数据库发布只能生效一次。

建议实现：事务领取 + `FOR UPDATE SKIP LOCKED`；有限指数退避；去重键；租约令牌；最大 attempt；dead-letter 查询页。SQL 写法和驱动版本在实施中通过集成测试确定，不能用进程内列表替代持久队列。

### 11.4 调度与资源上限

起步配置为单 Namespace 前台并发 1；全局前台并发上限 2；后台模型并发 1；同 Namespace 每类至多一个覆盖连续区间的活动作业。前台有优先配额，不被批量 TP 占满。数据库事务不能在等待外部 API 时保持行锁。

这些数值用于资源可控的首轮开发，不是吞吐承诺。接入真实 API 后按限流、内存和实测延迟调整，保存配置版本。

## 12. TP：轻量主题材料，而非完整任务结案快照

### 12.1 首版结构

默认预设少量主题，例如 `profile`、`preferences`、`task_decisions`、`project_technical_choices`，它们只是测试配置，不是所有产品共用的永久分类。每个主题保存简短介绍、条目集合、来源范围和更新时间。

条目只追加；同一来源已经形成的同配置条目不得重复新增。介绍变化产生新版本，可由目前条目生成，但每项可事实性主张必须能追溯到 Raw；旧介绍不是新的独立证据。

### 12.2 增量流程

读取 TP 自己尚未扫描且已被接纳的 Raw → 轻量匹配/分类 → 对相关材料生成分条摘要 → 校验引用和去重 → 事务提交条目、介绍版本及扫描游标。一个批次没有相关主题也记录 no-op 并推进“已扫描”游标。失败不错误地越过未处理范围。

Topic 作业读取自己的 Raw，不把 Episode 当唯一来源。它可以链接到任务，但无权将任务设为 completed。首版不自动创建无限新主题，主题增加由配置/人工控制。

### 12.3 如何进入回答

检索可先命中主题介绍，再在受限预算内展开少量条目或原文。主题介绍不是自动全量注入。开 TP 时记录目录检索、条目展开、最终采用的引用和相关成本。

关闭 TP 时：不调度新作业，不检索/注入已有 TP，不产生 TP 模型费用；已保存历史结果仍可在检查页面浏览。实验 D 使用新 Namespace，不能继承 C 或先前 D 运行形成的主题。

## 13. 检索：候选生成、版本过滤、融合与回查

### 13.1 索引对象

分别建立 Raw 片段、当前/历史事实、Episode 条目、TP 介绍/条目的可检索表示。大工具结果可按固定 chunk 规则索引。每个索引文档保留源 ID、源版本、顺序范围、Namespace、文本哈希和索引配置版本。

Raw 片段切分以消息/段落为主；长消息可再分块，记录与原文偏移映射。初始目标 500 tokens、重叠 50 tokens 仅作为配置起点；不要在比较实验中一边改摘要算法，一边无记录地改切分。

### 13.2 查询入口

第一版查询使用当前用户消息，加可选的 CTS 目标/未解决项，按固定模板拼接。不默认额外调用模型做查询重写。查询模式由明确的 `current/historical` 请求指定或规则判定；规则不能确定时可同时返回两类、清楚标记，并让回答说明歧义。

先应用权限、可见上限、删除状态、任务/会话范围，再运行索引候选生成。历史查询可包含旧版本；当前查询中同键旧值不能抢占新 head。历史问题“以前预算多少”不能因为只保留当前事实而被误答。

### 13.3 固定融合

每路默认取 20 条候选，用下式合并同一规范化文档：

```text
RRF(doc) = Σ_route 1 / (k + rank_route(doc)), k = 60
```

只对实际出现的排名计分；排名从 1 开始。先按规范化来源去重再返回候选；分数相同时按稳定 source ID 排序，避免偶发排序改变输入。融合后最多给 Context Builder 12 条候选，最终是否采用仍受预算限制。

k、top-k、路数都是初始实验配置，不声称它们最优。BM25 分数与向量相似度不同量纲，不直接相加。仅向量/仅 BM25 是两条可运行的附加对照，不把未启用路当返回空的故障路。

### 13.4 Raw 回查与工具

提供只读 `search_raw`、`read_raw_range`、`read_memory_source`。服务端注入 Namespace/cutoff；模型不能指定别的用户或绕过顺序过滤。每次调用限制返回条数、字符/token、次数。返回节选与 source ref，不自动复制整条数万 token 工具结果。

如果摘要没记错误码，Raw BM25 仍能命中原文。embedding 失败时，线上可降级为 BM25，但必须标为 `retrieval_degraded`；声明为 hybrid 的实验不能把这种运行算成正常 hybrid，默认标 invalid 或单独报告。

### 13.5 索引的一致性

源记录提交时写 outbox，索引 worker 消费后生成新的 index manifest。删除先封锁源记录查询，再异步清理索引，防止清理空隙泄漏。索引结果还要二次检查源记录存活和可见性。

离线实验默认在每个规定屏障等待所需索引完成，使用 `deterministic_barriers` 调度；线上允许有界延迟并记录实际 manifest。每次检索保存候选清单和 manifest，使过去的召回不会随着索引重建而“看起来变好”。两种调度成绩分别报告。 在离线 `deterministic_barriers` 模式，测试外壳可在预先规定的检查点等启用的派生作业（含 TP）完成后再发起评测请求；这属于实验准备屏障，不改变在线 Context Builder 不等待 TP 的规则。等待时间和后台成本仍计入总运行记录，不能把这种理想就绪条件当作线上延迟成绩。

## 14. Context Builder：四层布局、输入预算与冻结

### 14.1 四层逻辑内容

| 层 | 内容 | 保留规则 |
| --- | --- | --- |
| Rules | 应用固定规则、工具约束、实验任务说明；Pin 有清晰来源与数据身份 | 真正系统规则必须保留；用户 Pin 不是更高权限指令 |
| CTS | 当前任务状态和当前适用事实/约束的受控视图 | 当前目标、关键约束、未完成项优先；每项有版本 |
| History | 选中的事实、Episode、TP 及必要原文证据 | 去重、版本过滤、按预算选择 |
| Recent Raw | 最近若干完整对话/工具协议组及本轮输入 | 本轮输入和未闭合工具关联不可静默丢弃 |

四层是项目的逻辑排列，不代表四层都塞进 system 角色。适配器必须保持实际 API 支持的 message role 和工具配对。检索文本、用户记忆、网页/数据集内容以不可信数据分隔展示，不可因位于 Rules 区域就获得覆盖系统指令的权限。

没有当前任务时 CTS 可以为空；没有可用历史时 History 为空；日志明确标为空，不用“无记忆”占位句推断用户事实。

### 14.2 预算公式

```text
hard_context_limit = min(供应商已核实窗口, 项目配置上限)
request_limit = hard_context_limit - max_output_tokens - safety_margin_tokens
serialized_request_tokens = messages + tool_definitions + output_schema + protocol_overhead
发送条件：serialized_request_tokens <= request_limit
```

初始配置上限 16,384 tokens、输出预留 2,048、安全余量 1,024；因此请求预算上限为 13,312，前提是模型实际支持相应窗口。任何模型的真实限制小于配置时应缩小或拒绝，不能仅凭型号名推定。

优先使用准确 tokenizer/供应商计数能力；只有估计器时记录 `token_estimate_method` 并采用额外保守系数。安全余量不是准确保证；供应商报告超长时记为 `CONTEXT_LENGTH_EXCEEDED`，重新构建有新 Snapshot 和 attempt，不能假装原请求成功。

### 14.3 选择顺序

先放真正必需的固定规则、当前用户输入、关键任务约束、合法工具配对。再分配最近原文和历史；历史候选按效用/去重规则逐项装入。CTS/History/Recent 的分配是软目标，不能靠截断否定词/金额/JSON 半截来满足预算。

超过预算时依次处理：大工具结果外置；去重；减少低相关历史；缩小较早 Recent 的完整组；使用已发布 Episode；尝试必要的压缩交接。最终仍放不下必需内容，返回 `CONTEXT_BUDGET_EXCEEDED`。超过预算时必须让前端知道原因与实际估算，不能“自动忘记”最新要求。

候选排除原因至少支持：`duplicate`、`superseded`、`scope_mismatch`、`future_source`、`deleted_source`、`budget_limit`、`strategy_disabled`、`index_not_ready`。

### 14.4 Snapshot 必须保存什么

保存逻辑四层、每段 source/version、检索运行 ID、cutoff、状态 revision、coverage、索引 manifest、配置/提示词版本、输出预算、估计方法、最终序列化请求体及内容哈希。真正请求体不包含 Authorization 等秘密字段；哈希针对实际非秘密模型 payload。

发送前检查 Namespace/epoch 和中断；写 `prepared` Snapshot，再分配 Call attempt。供应商实际接受后记录 request ID（若可得）和 `sent` 状态。网络超时无法判断是否受理时标 `unknown_outcome`；重发可能再次收费，记录新 attempt。过去 Snapshot 不因后来事实修正而改写，只有依法/按用户要求删除内容时可转为不可读取墓碑。

## 15. 大工具结果与模型接入

### 15.1 工具结果外置

完整结果存持久 artifact，Raw 保留 content_ref、哈希、长度及调用关系。模型收到一个合法 tool result，正文为有限预览、稳定 artifact_id、如何读取的说明。后续只能通过受限 `read_artifact` 读取。默认工具结果超过 2,000 估计 tokens 时外置，预览目标 600；参数可配置。

artifact_id 不是文件路径。禁止将用户参数直接拼成本地路径；读取校验 Namespace、cutoff 和删除状态。索引原文失败不删除原始结果。历史里已完成工具组可以整体被摘要替换，活跃工具调用与结果必须保持协议合法。

首版提供三个只读测试工具：固定候选集合查询、原文检索、artifact 分段读取。必须有确定性 fixture 工具以测试任务进展与约束选择。真正业务工具另行接入，不纳入首版评测的隐含依赖。

### 15.2 模型网关接口

网关抽象最低支持：`generate`、`stream`、`embed`（可由另一供应商提供）、`count_or_estimate_tokens`、`capabilities`。返回规范化消息、工具调用、供应商原始响应引用、usage、finish_reason、request_id 与错误。

首版至少验证一个生成 API 和一个 embedding 模型。DeepSeek/Qwen 是候选，不要求两家同时完成。OpenAI 兼容仅作为协议适配方向，不假设所有供应商都支持相同的 JSON Schema、tool calling、思考参数和 usage 字段。上线前逐项探测流式、工具、结构化输出、长度限制、限流、错误码和地区 endpoint。

JSON mode 不等于语义正确；schema 通过后仍执行证据与版本校验。没有 strict schema 能力时用固定提示词输出 JSON + 本地校验 + 有限修复。不得把解析失败后提取出的零散字段当有效变更。

### 15.3 调用成本与重试

每个用途分开累计：answer、memory_update、episode、topic、embedding、judge、repair。保存供应商输入/输出/缓存用量（可得时）、本地估计、价目版本、币种、计算值及是否估算。未知费用用 null 和 unknown，不填 0；不同币种不直接相加。

瞬时网络故障/限流/部分 5xx 可有限重试；无效密钥、权限和明确格式配置错误不盲目重试。重试前检查取消、预算和 epoch。生成请求可能重复收费，写工具不可照搬重试。批量实验必须设置最大调用数、token 和可选金额限额；金额定价不明时至少用调用/token 限额止损。

## 16. HTTP API 与 SSE 契约

### 16.1 通用约定

对外前缀 `/api/v1`，经 Spring Boot 鉴权后代理到 Python `/internal/v1`。内部请求采用服务凭据并携带经验证的主体上下文；不得仅凭来自浏览器的同名 header 信任身份。所有列表分页，默认 50、上限 200；全文/附件按范围读取。

成功响应结构为 `{data, request_id}`；错误结构如下。`POST` 创建写操作必须支持 `Idempotency-Key`。相同键和相同规范化正文返回原对象；不同正文返回 HTTP 409。校验错误不得已经触发收费调用。

```json
{
  "error": {
    "code": "STATE_VERSION_CONFLICT",
    "message": "记忆状态已经变化，请基于最新版本重新提交。",
    "retryable": true,
    "details": {"expected_revision": 7, "actual_revision": 8}
  },
  "request_id": "req_demo"
}
```

用户不可见的其他 Namespace 返回 404 或统一的访问拒绝，不通过详细错误泄漏记录是否存在。所有 write 返回持久对象 ID；所有 async 操作返回状态查询地址，不只返回“已提交”。

### 16.2 会话、任务与运行检查接口

| 方法与路径（省略前缀） | 请求 | 返回/行为 |
| --- | --- | --- |

| `GET /namespaces/{ns}/sessions` | cursor?, limit? | 会话列表 |


```json
{"data":{"ingress_id":"in_12","status":"queued","poll_url":"/api/v1/ingress/in_12"},"request_id":"req_12"}
```

| `POST /namespaces/{ns}/deletions` | event_ids, include_derived=true | 定向删除并重建派生状态，见第 18 节 |
| `GET /deletions/{id}` | 无 | 撤销、清理、重建及失败状态 |

浏览器的 `/raw` 全历史权限不等于模型工具权限。模型工具必须走独立受限方法，强制当前 cutoff，不能直接调用开发者检查页面的 API。

### 16.4 配置、数据、实验接口

| 方法与路径 | 请求/参数 | 返回/行为 |
| --- | --- | --- |
| `GET /configs` | kind? | 模型/策略/提示词配置版本 |
| `POST /configs` | kind, content, parent_version? | 校验后创建新版本 |
| `POST /configs/{id}/validate` | probe=true/false | 静态校验；probe 需说明可能触发调用费用 |
| `GET /datasets` | 无 | 数据集 manifest、审计和许可状态 |
| `GET /datasets/{id}/trajectories` | split?, audit_status?, cursor? | 轨迹元数据，不默认携带所有 gold |
| `POST /runs` | dataset_manifest, trajectory_ids, strategy_config, mode, schedule_mode, caps | 冻结配置并新建隔离 Namespace；返回 run_id |
| `POST /runs/{id}/actions` | action=step/start/pause/cancel | 按既定轨迹前进；单步不允许读取未来 |
| `GET /runs/{id}` | 无 | manifest、进度、状态、成本、失败统计 |
| `GET /runs/{id}/results` | metric?, cursor? | 逐项评分，分母、invalid/unscored 必须可见 |
| `GET /runs/{id}/gold` | evaluator/debug 权限 | 开发者查看标签；不对 Agent 服务凭据开放 |
| `POST /runs/{id}/branches` | checkpoint_id, new_config, kind=intervention | 新 Namespace；清晰标为中途干预 |
| `POST /comparisons` | run_ids | 校验可比性，返回差异视图或不匹配项 |
| `POST /runs/{id}/exports` | include_raw=false, format=zip | 脱敏导出作业；原文导出需明确授权 |

OpenAPI 必须落实上述请求/响应模型、状态码、必填字段、枚举、分页和授权范围。前端使用生成的类型；不靠复制几段 JSON 维护两套接口定义。

### 16.5 SSE

每条 SSE 具有单调递增 `id`、`event` 名称和 JSON `data`。事件类型最低包含：`ingress.admitted`、`turn.started`、`memory.proposed`、`memory.committed`、`retrieval.completed`、`context.frozen`、`answer.delta`、`call.completed`、`job.status`、`turn.completed`、`turn.failed`、`turn.interrupted`。

只向有权用户发送；delta 先持久或分批落盘后再承诺可恢复。断线时客户端用 Last-Event-ID 续读；事件已过保留期则返回重同步指令，客户端读取 Turn 当前状态及持久最终答案。断线不是“再次生成”的理由。流式碎片重放按 stream_seq 去重，最终回答与持久结果一致。

### 16.6 最低错误码

`VALIDATION_ERROR`、`IDEMPOTENCY_CONFLICT`、`NOT_FOUND`、`ACCESS_DENIED`、`NAMESPACE_DELETED`、`STALE_EPOCH`、`STATE_VERSION_CONFLICT`、`FUTURE_EVIDENCE`、`INVALID_EVIDENCE`、`MEMORY_UPDATE_FAILED`、`COMPACTION_REQUIRED`、`CONTEXT_BUDGET_EXCEEDED`、`PROVIDER_RATE_LIMIT`、`PROVIDER_TIMEOUT`、`PROVIDER_RESPONSE_INVALID`、`MODEL_CAPABILITY_MISSING`、`INDEX_NOT_READY`、`RUN_BUDGET_EXCEEDED`、`AGENT_ITERATION_LIMIT`。

每个错误注明是否可重试、是否已经产生费用、是否改变状态。前端不得把所有错误统一显示成“网络异常”。

## 17. 可观察性：记录发生什么，不伪造模型内部过程

### 17.1 一个 Turn 的证据链

从回答反查 Call → Snapshot → Retrieval → Fact/CTS/Episode/TP 版本 → Raw 来源。反向也可从某条 Raw 查它引起的事实变化和在哪些输入快照中出现。

“进入模型输入”是可证明的事实；“模型内部实际关注这条信息”不是日志能证明的事实。界面使用“已送入输入”，不使用“模型思考时使用了”这种无依据描述。

### 17.2 记录最小集合

| 阶段 | 必须保存 |
| --- | --- |
| 输入接收 | 原内容哈希、接收时间、幂等键、排队与接纳时间 |
| 更新 | 输入版本、候选操作、来源、拒绝原因、实际提交与 diff |
| 摘要 | 区间、当时状态、请求、输出、校验、发布结果、coverage |
| 检索 | 查询、过滤范围、索引版本、各路排名、融合和排除 |
| 构建 | 四层内容、预算分配、最终请求、选取原因 |
| 调用 | model/provider/config、request/response、attempt、usage、finish_reason |
| 工具 | 参数、调用 ID、权限结果、真实返回、artifact 引用、取消/重试 |
| 实验 | 数据版本、split、模式、运行依赖、评分器版本、每项结论 |

开发日志打印 request_id/namespace_id/turn_id/call_id/job_id，默认不打印整段用户原文和密钥。调试面板的敏感内容由权限控制，不把“为了可观察”当成公开存储所有私人对话的理由。

### 17.3 性能与成本

分别计算接收确认延迟、队列等待、记忆更新时间、压缩交接等待、检索/构建时间、主调用首字时间、生成总时长、Turn 端到端时长、TP 延迟、索引延迟。总成本包括后台与评分，另外报告“不含评分的运行成本”，不混为一个未定义指标。

小批样本的 p95 仅描述这批观测，不能宣称稳定吞吐能力。模拟模型用于工程负载测试，真实 API 用于端到端小规模测试，两者分别报告。

## 18. 关闭、取消、删除与恢复

### 18.1 不同操作的语义

关闭会话：不再默认显示，数据保留。暂停任务：停止当前推进，状态可恢复。取消 Turn：停止后续执行，已经完成的调用与原始记录保留。停止主动使用某条事实：撤销当前 head 或加 suppression，不等于删数据。删除：立即撤销读取，并清理对应原始和派生内容。

### 18.2 Namespace 删除

在事务中标记 deleting，递增 generation_epoch，撤销接纳/检索/导出权限，取消未执行作业。所有正在运行的 worker 在提交前检查 epoch，迟到结果作 obsolete，不能写回。

随后清理 Raw、Ingress、事实、CTS、Episode、TP、索引、artifact、缓存、执行检查点、输入快照、流式事件和未交付导出。仅保留不含原文/值的删除状态及必要计数。对象内容若共享，需要按引用计数与权限处理，不删除别的 Namespace 的合法数据。

如果某请求已经发送到模型供应商，本地删除不能撤回对方已经接收到的内容；供应商保留策略需单独核对。历史备份、用户已下载的导出也不能被本地接口自动擦除；部署说明必须列出备份保留与清理流程，不能承诺范围外的绝对删除。

### 18.3 定向删除与派生失效

删某些 Raw/事实来源时，立即屏蔽来源及所有依赖它们的派生内容。首版选择保守实现：**新 epoch 下使该 Namespace 的全部派生记忆失效，从剩余允许保留的 Raw 重建**，而不冒险从复杂摘要中删除几个字。

重建期间 Namespace 为 rebuilding，不生成依赖不完整记忆的建议。事实不自动回退成旧值，必须重新计算并可审查。coverage/revision 在一个 epoch 内单调前进；重建开启新 epoch 后可以从新起点计算，不能把两个 epoch 的数字直接比较。

定向删除不自动删除上游公开数据仓库；用户删除实验运行与删除所下载原数据是不同范围。禁止将被删除 Namespace 的检查点分支恢复成新运行绕过撤销。

### 18.4 进程恢复

启动时加载未结束 Turn、过期租约、未消费 outbox 与待完成删除。模型请求 sent 但未拿到响应时标 unknown_outcome，按策略决定重新调用，绝不能假定没有计费。工具结果已保存则复用结果；不再次执行已完成动作。

SSE 恢复读取持久状态；索引可以重建；事实更新通过操作唯一键避免重复；Episode 发布通过 coverage/epoch CAS 防止双重提交。重启测试必须覆盖“调用已返回但提交前”“提交完成但响应客户端前”两个窗口。

## 19. 数据接入与连续回放

### 19.1 首版实际接入范围

人工功能轨迹用于明确行为验收；首批 20—30 条 MemOps 完整轨迹用于审计和诊断。PersonaMem-v2、LongMemEval、MemoryArena 不作为首版运行依赖。来源说明沿用配套数据源文件，本次没有重新下载或验证这些数据集的最新版本。

适配器必须输出：不可变数据 manifest、模型可见的分时事件、evaluator 专用检查点标签、证据映射、审计记录、分组划分和校验报告。不要把它们打包成一个会整体送进模型的 JSON。

### 19.2 同一核心，两种数据进入方式

在线：浏览器输入 → Ingress → Raw → 核心。离线：只读轨迹中的下一个消息 → Ingress → Raw → 核心。标准答案不进入此路径。

固定流回放使用事件级入口，只调用同一核心的接纳、状态更新、派生处理和构建能力，不机械调用第 9 节会自动生成主回答的完整交互外壳。历史 Turn/工具组边界按源角色与关联关系确定；下一用户消息到来或原助手回答结束可关闭合法历史组，不伪造一段助手回答来凑边界。

离线回放依旧保留历史角色。数据集提供的助手历史应按原有顺序进入历史；其源身份标注清楚，不将它改成用户消息。检测用户触发的更新时，先检查这一刻结果，再接纳源数据中随后出现的助手确认，不能提前喂给更新器。

### 19.3 三种模式必须命名清楚

| mode | 做法 | 可回答的问题 |
| --- | --- | --- |
| `single_step_gold_state` | 每项使用同一正确先前状态；只检查该步候选与提交 | 更新器本身是否理解这一步 |
| `continuous_fixed_stream` | 各系统持续使用自己的记忆；外部历史流固定；指定检查点提问 | 记忆是否累积错误，是否改善后续读取/选择 |
| `interactive_demo` | 用户与本系统生成的回答继续互动 | 在线产品流程是否顺畅；不直接等于公开数据集成绩 |

在固定流模式，生成的检查问题回答默认不写回主轨迹；用隔离 probe 子运行执行，防止一次问答为后面提供答案。需要研究反馈回流时另设显式模式，不能混在同一分数里。

### 19.4 标签隔离和已知字段诊断

`target_key/expected_action/expected_value/gold_state` 由 evaluator 持有。已知字段诊断可以把待判断的字段名提供给模型，但必须标为 `target_mode=known_field`；不提供时为 `discovery`，两者分开评分。被测运行不读取完整人物档案、未来事件或评分用证据列表。

访问控制测试必须真实尝试从 Agent 连接查询标签和未来数据，预期被拒绝；只在提示词写“别看答案”不算隔离。

## 20. 运行配置、四组基线与分支

### 20.1 基线配置

| ID | enabled modules | 可比较的指标 |
| --- | --- | --- |
| A `recent_window` | Raw、相同固定规则/只读工具、预算内 Recent；无事实更新、CTS、Episode、TP 检索 | 最终问答/决策、成本；没有内部事实指标时为 N/A |
| B `rolling_summary` | A + 普通滚动摘要；允许旧摘要加新 Raw 的递归更新；无结构事实/CTS/TP | 相同外部任务表现和成本 |
| C `core_no_tp` | Raw、当前事实、CTS、Raw-based Episode、双路检索、四层构建、工具外置 | 外部结果及内部记忆指标 |
| D `core_with_tp` | C + 轻量 TP | 在同等条件下 TP 的增量收益/成本 |

基础执行安全、权限、工具协议、事件保存、调用记录、相同预算上限为所有配置共同能力。共同的“工具”指固定候选查询等业务工具及当前已授权 artifact 读取；Raw/记忆检索工具是记忆策略的一部分，A/B 不开放，C/D 可开放。整套 A/B/C/D 是系统方案比较，不能仅凭其差异断言某一个模块带来全部收益；单模块消融再固定其余工具。A/B 不得从影子运行的 C 中偷取事实/CTS；所谓关闭模块也不得在后台继续付费生成。B 的普通摘要有单独 schema 和覆盖记录，不能混进 C 的非递归 Episode 表示。

当前事实表和 CTS 缺失的方案不能被记作更新正确率 0%；该指标应为不适用。跨系统主比较用所有方案都承担的最终任务；C/D 之间才比较对应内部操作指标。

### 20.2 Run manifest

至少保存：run_id、namespace_id、parent_run/checkpoint（如有）、代码提交号、dirty 状态及补丁哈希、数据与 split manifest 哈希、样本 ID、运行模式、策略配置、提示词版本、供应商/模型 ID/可取得版本、embedding/分词/chunk 版本、输入输出预算、采样参数/seed（支持时）、索引 manifest、调度模式、评分规则、时间、调用上限、价格配置和环境版本。

商业 API 可能变化；固定别名与 seed 不能保证完全复现，实际请求和响应必须保存。实验可比性校验应列出所有不同字段，而不是只看两个运行用了同名模型。

### 20.3 查看、重跑与分支

查看记录：不调用模型。重新运行：新 Namespace，从原数据起点运行，可能有新费用与不同结果。分支：在某个一致性检查点复制可见前缀和状态到新 Namespace，明确标为中途干预实验。

检查点必须在没有未提交前台状态变更的边界创建，包含 Raw 位置、状态 revision、事实/CTS 版本、Episode/TP、索引 manifest、pending jobs 描述、配置和 epoch。LangGraph checkpoint 仅是组成部分，不能当成外部数据库的完整快照。

分支重新映射本地记录 ID 与 Namespace，保留 `origin_id` 供对照。共享只读字节也必须有新 Namespace 授权包装。新作业在分支 Namespace 重新排队，不能让原 worker 写到分支；被删除来源不得复制恢复。

更换压缩策略后，要评估完整方法就从 Raw 起点重跑；从已有摘要继续只是中途换策略实验，报告中必须如此命名。

## 21. 评测：判定依据、指标与错误定位

### 21.1 优先评分顺序

首先用确定性校验：规范化值匹配、状态版本、范围、证据引用、候选约束、来源泄漏和事务行为。对语义表述需要人工审查或独立评分模型；评分模型仅由 evaluator 调用，固定提示词和版本，保存评分理由与不确定结果。

不要让被测模型自己说“我记对了”就算通过。评分模型只是辅助，不是未经审计的绝对真值；人工审查集和一致性记录必须保留。

### 21.2 指标定义

| 指标 | 计算口径 |
| --- | --- |
| 操作准确率 | 标注范围内正确 ADD/UPDATE/KEEP 数 / 有效且适用的已评分检查点数；另报各类分母 |
| 当前值准确率 | 在指定时点与规范化 gold 当前值匹配的字段数 / 有 gold 的字段数 |
| 误覆盖率 | gold 为 KEEP 或无权修改时，错误改变当前 head 的项数 / 相应检查项数 |
| 范围/主体错误 | 写错用户、任务、会话或对象的项数，单独计数 |
| 证据支持率 | 引用存在且内容确实支持结论的操作数 / 被审查的操作数；存在性和语义支持分开 |
| 旧值使用率 | 必须用新值的后续回答却使用旧值的次数 / 相应问题数 |
| 检索证据命中 | gold 证据进入候选/进入最终输入分别统计；只有存在可靠证据标签时计算 |
| 后续问答准确率 | 评分规则判对的问题数 / 可评分问题数；unknown/unscored 单列 |
| 受约束选择正确率 | 满足预先定义选择规则的结果数 / 相应探针数；与满意度区分 |
| 系统完成率 | 到达正常终点轨迹数 / 所有启动轨迹数；失败/取消/超预算列出 |
| 成本与延迟 | 全部实际调用总计；未知计价不能填零；前后台、评分分开 |

无分母时显示 N/A，不显示 0%。分组报告新增/纠正/条件/主体/长干扰等类别。对少量轨迹同时给逐项表，不只给一个小数点很精细的平均数。后续估计区间以人物/轨迹为重采样单位，不能假设同人物每一轮互相独立。

### 21.3 错误定位

`ingestion` 接纳/顺序错误 → `memory_extraction` 候选错误 → `commit` 提交错误 → `compaction` 摘要错误 → `retrieval` 未找回 → `context_selection` 找回但未送入 → `answer_use` 输入充分却答错 → `scoring` 标签/评分问题。

允许一条轨迹有多个标签；优先标最早可证实的错误，而不是把所有失败归为“模型幻觉”。接口故障、预算失败、语义错误和标签不确定分别报告。

## 22. 安全、部署与开发环境

### 22.1 最小部署

Docker Compose 至少包含 web/app-api、agent-api、worker、PostgreSQL/pgvector，及持久卷。数据库迁移由明确入口执行一次；进程启动验证 schema 版本。BM25 可由 agent 服务加载可重建快照，重建输入为数据库中授权可见源。

开发模式仅监听本机，固定开发用户只能在 dev 配置启用；访问远程服务器时必须启用鉴权、TLS、受控 CORS、请求大小限制和速率限制。模型密钥、数据库密码、原始私人对话不进入 Git。环境示例只放变量名。

### 22.2 最低配置检查

未填写生成模型、embedding 模型、地区 base URL 或已核实上下文上限时，真实 API 模式拒绝启动并明确提示缺项。离线 fixture 模式不要求真实密钥。选定库版本后提交 lock 文件，实际兼容性由冒烟测试验证，本计划不虚构已经锁定的最新版本。

### 22.3 持续集成

单元测试使用模型桩，不访问收费 API；集成测试使用临时 PostgreSQL；合约测试验证前后端 schema；端到端测试验证四个工作区和事件顺序；真实 API 冒烟测试需要显式环境开关，默认不在每次提交运行。

代码提交前运行格式检查、类型检查、schema 校验、迁移往返/升级测试、单元与关键集成测试。结果和敏感样本默认不进 Git；记录可重建 manifest 和脱敏结果。

## 23. 开发阶段与任务拆分

每阶段结束都应有可演示界面或可自动验证结果。依赖关系先解决正确性，再扩大模型能力；不把“接入所有模型”作为阶段一任务。

| 阶段 | 任务编号与内容 | 具体交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P1 契约与样例 | P1-01 ID/归属/顺序；P1-02 schema/OpenAPI；P1-03 人工轨迹；P1-04 决策与配置 | 领域模型、迁移草案、fixture、验收表 | 可见性/幂等/基本状态规则能用桩测试 |
| P2 前后端骨架 | P2-01 Compose；P2-02 鉴权与 Ingress；P2-03 模型网关；P2-04 SSE/Raw/Call | 可聊天、可查看真实请求、可断线恢复 | 重复发送无重复 Raw；重启后历史可读 |
| P3 当前记忆与 CTS | P3-01 更新 schema/提示词；P3-02 CAS 提交；P3-03 任务控制；P3-04 记忆页面 | 版本/来源/diff、任务恢复、受控跨会话 | 关键纠正/条件/主体/范围样例通过 |
| P4 检索与构建 | P4-01 Raw 索引；P4-02 embedding；P4-03 固定融合；P4-04 四层/预算/快照；P4-05 大结果 | 可查候选与实际输入，原文可回查 | 摘要遗漏原文仍可查，预算及工具协议测试通过 |
| P5 Episode/TP/生命周期 | P5-01 作业租约；P5-02 Episode；P5-03 交接/回退；P5-04 TP；P5-05 删除/重启 | 后台面板，长历史，独立 TP，故障恢复 | 迟到覆盖/删除写回/重复发布测试通过 |
| P6 数据与实验 | P6-01 MemOps 审计与适配；P6-02 回放器；P6-03 A/B/C/D；P6-04 评分；P6-05 分支导出 | 第一批运行结果、差异页面、失败分析 | 数据隔离检查通过；真实运行与费用记录完整 |

每个任务需在 issue 中标记“尚未开始/开发中/已联调/已验收”，并附实现路径、测试 ID 和演示记录。不能把“提示词写完”直接标成模块完成。数据库隔离、来源和日志随每阶段建设，不留到 P6 一次补救。

## 24. 可执行验收矩阵

### 24.1 确定性工程测试（使用模型/工具桩，必须全通过）

| ID | 输入或故障 | 预期行为 |
| --- | --- | --- |
| T01 | 同一幂等键发送两次同正文 | 同一 Ingress/Raw，不重复模型执行 |
| T02 | 同键不同正文 | 409；无第二次写入/收费调用 |
| T03 | 更新预算 500→300 的合法候选 | 当前 head=300，旧版仍在，CTS 约束一致 |
| T04 | 明确 KEEP 候选 | 该 fact_head 的版本不发生伪修改；操作日志存在（投影进度仍可前进） |
| T05 | 候选 expected_version 已过期 | 拒绝/重新判断，不强行覆盖 |
| T06 | 候选引用未来事件或别的 Namespace | 拒绝提交，记录 FUTURE_EVIDENCE/访问错误 |
| T07 | 源中工具 call 尚无 result | 不生成截断配对的请求/压缩边界 |
| T08 | 当前调用中收到新输入 | 立即持久保存；当前快照不变；下次相关调用先处理新输入 |
| T09 | Episode 整理旧区间时用户更新事实 | 新事实保持有效；Episode 发布不写事实表 |
| T10 | 两个 worker 同时发布同一区间 | 仅一次有效发布和 coverage 前进 |
| T11 | Episode 超时但 Raw 能放下 | 明确降级、保留来源、coverage 不虚增 |
| T12 | Episode 失败且必要输入超预算 | COMPACTION_REQUIRED，不静默丢最新要求 |
| T13 | TP 变慢/失败/关闭 | 主调用不等待；关闭无 TP 调用与输入 |
| T14 | 摘要未包含错误码，但 Raw 有 | search_raw 命中正确原文及引用 |
| T15 | 当前事实旧版本排名高于新版本 | 当前模式不让旧值盖过新值；历史模式仍能查旧值 |
| T16 | 删除时后台模型刚返回 | epoch 检查阻止写回，来源查询立即不可见 |
| T17 | 已提交事务后进程崩溃、客户端重试 | 返回同一结果，无重复事实/条目 |
| T18 | SSE 断线后续读 | 不重复 token/消息，不触发新生成 |
| T19 | 实验 A/B/C/D 使用同轨迹 | 可变记忆/作业/索引互不串用 |
| T20 | Agent 试读 gold 或原数据未来事件 | 凭据/工具接口拒绝；不靠提示词自觉 |
| T21 | 更换 embedding 维度/模型 | 新 manifest；不把不兼容向量混检 |
| T22 | 大工具结果外置 | 完整原文可回查，消息协议仍合法，预算包含工具定义 |
| T23 | 从含已删除来源的检查点分支 | 拒绝恢复被删内容 |
| T24 | 固定流中的一次 probe 回答 | 默认不写回主轨迹，不给后面泄漏答案 |
| T25 | 中文、emoji 引用偏移 | 截取正确原文，前后端一致 |
| T26 | 供应商 usage/价格缺失 | 显示 unknown，不伪报零成本 |
| T27 | 同一 Namespace 跨会话不同任务 | 长期明示信息可读，旧任务预算不自动迁移 |
| T28 | 工具已返回、进程恢复 | 复用已保存结果，不重复调用 |

### 24.2 人工轨迹与真实模型冒烟

至少准备：明确新增、明确纠正、条件变化、未来计划、提到他人、任务临时约束、跨会话长期明示、任务切换恢复、长干扰旧值、工具反馈与选择这 10 类完整轨迹。每条含预期状态、关键证据和后续问题，不能只是 10 条互不相关的句子。

真实模型运行必须展示预算更新/条件保持/任务恢复/长历史回查的实际结果。失败逐项记录和修复；不要求 MemOps 全部答对才能交付研究平台，也不允许把真实模型失败用桩结果替代。验收报告分开列“工程测试通过”与“模型行为成绩”。

### 24.3 完成定义

首版完成须同时满足：T01—T28 工程测试通过；四个工作区可用；一个生成 API 和一个 embedding 配置已冒烟；A/B/C/D 真正运行；人工轨迹有完整记录；首批 MemOps 有审计、许可记录、转换报告与连续运行结果；失败可定位；成本不遗漏后台；开发者能按 README 启动并从空数据库复现流程。

这定义的是要完成的验收，不表示本次文档编写已经执行这些测试。所有性能数字、模型效果和数据许可仍以实现时的实际记录为准。

## 25. 首版交付与研究记录格式

代码交付：前后端、核心、worker、适配器、基线、评分器、迁移、配置和测试。数据交付：manifest、审计、split、脱敏转换样例、许可允许的实际子集或下载指令。结果交付：逐轨迹/逐检查点结果、调用和成本、失败案例、环境及可比性报告。

一次实验导出至少包括：`run_manifest.json`、`metrics.json`、`case_results.jsonl`、`errors.jsonl`、`costs.json`、`configuration/`、`source_manifest.json`。原文/请求体可单独授权导出，默认脱敏，不把 API key 或外部账户凭据放进去。

研究结论模板：这次只改变了什么；保持了什么；样本/分组是什么；哪些结果变好/变坏；成本变化；证据与失败案例；不确定性；是否接纳为新的默认配置。没有实际运行数据时只记录假设，不填“提升 x%”。

## 26. 初始配置与开发前待填项

`开发附件/default.yaml` 给出规范化起步参数，`strategies.yaml` 给出四组开关。它们是本项目约定的配置，不是任何外部框架的原生配置；实施时需提供对应加载器并做校验。

| 待填项 | 如何决定 | 是否阻塞代码骨架 |
| --- | --- | --- |
| 生成模型 ID、base URL、地区和密钥 | 从本人可用账户选择，按网关能力逐项探测 | 不阻塞 fixture；阻塞真实 API 模式 |
| embedding 模型、维度与语言覆盖 | 固定一个，跑中英文/错误码小测试 | 不阻塞 BM25；阻塞 hybrid 实验 |
| 真实窗口/输出限制/计价 | 保存官方配置来源与探测时间 | 阻塞真实成本与长度承诺 |
| 库与数据库具体版本 | 安装时核对兼容性，提交 lock/image digest | 阻塞部署锁定，不改变模块边界 |
| MemOps 实际提交、许可证、20—30 条轨迹 | 下载后审计并记录 manifest | 阻塞公开数据运行，不阻塞人工验收 |
| 第一个正式业务领域 | 产品阶段另定；研究原型使用测试域 | 不阻塞首版研究平台 |

不得把待填值写成假装可用的密钥/模型名。配置校验应明确报错，而不是默默选择某家默认模型。默认参数未经本项目实测，不作为性能结论。
