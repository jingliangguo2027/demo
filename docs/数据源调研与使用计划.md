# 数据源调研与使用计划

原记录日期：2026-10-12。本次修订日期：2026-10-12。版本：`v1.0-data-spec`。

本文与[第一版实现计划](./第一版实现计划.md)、[第一版后深入研究计划](./第一版后深入研究计划.md)配套。第 1—5 节保留上传原文的数据角色和研究主线，并把小批 MemOps 审计、适配和回放纳入扩大后的第一版 P6；第 6 节以后新增开发契约。

**状态与来源边界：**上游材料的描述沿用用户上传的原文件；原文件记录来源核对日期为 2026-10-12，本次没有重新下载数据、核实最新上游提交/许可、完成人工审计、训练或运行模型评测。下文示例由本项目人工构造，不冒充 MemOps 原始样本或实际运行结果。工程字段和评分细则属于本次新增约定。

## 1. 先回答什么问题

项目目标是：**在固定基础模型和输入条件下，通过数据设计与后训练，让 Agent 更可靠地更新用户记忆，并改善后续多轮决策。**

数据要分别支持三个可检查的结果：①新信息是否被正确写入或用于替换旧信息；②隔了多轮后，系统是否仍使用当前有效信息；③记忆变化是否改善了后续可判定的选择或行动。最终答案正确，并不能单独说明记忆更新过程正确；答对记忆问答，也不能直接证明真实用户更满意。

**推荐顺序：先做少量人工检查样例 → 用 MemOps 建立第一轮更新实验 → 再用其他来源检验偏好、长历史与多步行动。** 第一版系统先使用现成模型和提示词；训练比较在基础版可回放之后进行。此次记录的数据源角色是方案，不表示已经通过项目验证。

## 2. 数据源各负责哪一段

| 数据源与官方入口 | 已公开的材料 | 在本项目中的建议用法 | 使用阶段 |
| --- | --- | --- | --- |
| [MemOps](https://github.com/MemTensor/MemOps) | 有对话、记忆操作、触发位置、目标、新旧值、证据位置和后续问题；仓库提供短证据对话及加入干扰的较长版本。 | **第一轮主数据源。** 先从短证据对话提取“建立信息、明确更新、保持当前信息”的样例，做记忆更新与连续回放；随后用较长版本检验干扰和陈旧值。 | 第一版 P6：人工功能验收通过后纳入小批审计、适配和回放；不含训练 |
| [PersonaMem-v2](https://github.com/bowen-upenn/PersonaMem-v2)／[数据卡](https://huggingface.co/datasets/bowen-upenn/PersonaMem-v2) | 模拟用户的对话、偏好、偏好变化和个性化问答；长历史含有隐含表达的偏好。 | 第二阶段检验“能否从含蓄表达中理解偏好”以及使用偏好回答后续问题。先抽取文本短片段做审计；不把数据卡中的完整人物设定当成模型在当时已知的输入。 | MemOps 更新实验稳定后 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval)／[清理版数据](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned) | 长历史问答，覆盖信息提取、跨会话推理、知识更新、时间推理和应当回答“不知道”的情况；官方提供清理版和证据范围较小的版本。 | 保留为**外部评测**：在固定输入预算下检查历史查找、更新后旧值使用和拒答。先抽样运行；证据范围较小的版本单独作为排错对照。 | 第一轮更新实验之后 |
| [MemoryArena](https://github.com/ZexueHe/MemoryArena)／[论文](https://arxiv.org/abs/2602.16313) | 多阶段 Agent 与环境交互任务，先前行动和反馈会影响后续行动；公开代码仍标为预览版。 | 后续检验记忆能否支撑多步任务。先选与用户约束或偏好相关的任务，固定 Agent、环境和评分方式，只替换记忆方案。 | 已有稳定多轮回放与评测后 |

另有一类**目前没有现成可靠来源**的数据：真实用户面对哪些候选、做了什么选择、为什么选择、实际体验如何。将来选定产品领域后，需要设计经用户许可的记录与反馈流程。公开合成数据支持受控能力研究；真实用户满意度和推荐收益需要相应的真实反馈来检验。这个边界也记录在[产品方向与技术选型](./产品方向与技术选型.md)中。

## 3. 首次使用 MemOps：具体步骤

### 步骤 A：先做小规模人工审计

从短证据材料（仓库的 `generated_result/2-evidence_conversation/`）抽取约 20—30 条**完整轨迹**，逐条阅读原文、操作标注和后续问题。检查标注是否能由当时已出现的证据判断，特别看“如果……才……”“暂定”“已经改主意”和提到他人的信息。记录不清楚或不适合本任务的样例；这一步产出的是审计记录，不是训练成绩。

### 步骤 B：先划分，再转换

按原始背景／人物对轨迹分组，固定训练、调试和最终测试的划分。首批被完整审阅并用于改程序的 20—30 条默认归为审计/调试数据，不再将其当作未接触的最终测试；更完整的数据划分按第 7 节执行。同一背景生成的不同对话、短证据与长历史版本、相关问答保持在同一组，避免测试集出现训练材料的近似副本。最终测试样例及答案保留到评测时使用。

把对话按时间映射为项目的 Raw 事件，并保留角色、顺序和原文位置。对每次待判断的操作，只向模型提供**截至触发时刻已经出现**的对话与当前记忆；不要提供未来轮次、完整背景设定或标准答案。当前轮用户发言之后的助手确认语句也不应提前进入这一轮的更新输入。

### 步骤 C：建立清楚的更新接口，为后续训练复用

第一轮只覆盖三种结果：**建立一个已确认的信息、用已确认的新值更新旧信息、保持当前值**。它们是本项目拟定义的训练输出，需由上游标注审计后映射，不能假定与上游标签逐项相同。每条转换后的样例至少保留：轨迹 ID、可见事件范围、目标信息及适用范围、原文证据、更新前的当前值、期望动作与期望值。

MemOps 中的 `Forget` 和 `Reflect` 先留作独立研究项。尤其要先区分“当前值被替换”“不再主动提起某信息”“按用户要求遗忘信息”及“删除数据”的不同语义。未标注某个事实，也不能直接推断整轮对话毫无可保存内容。最初可以用已知目标字段做**受控诊断**；系统自行发现所有应更新字段，则是另一个待测能力。

### 步骤 D：首版先跑未训练基线，后续再做小规模后训练

首版 P6 到未训练基线与回放结果为止；下面涉及训练的比较是第一版后的工作，不是首版交付条件。

在同一套事件记录、提交规则、检索、上下文预算和后续决策模型下，比较：①第一版的提示词更新策略；②经过审计的数据训练出的更新策略。固定基础模型版本，逐次记录模型提出的变更、证据、实际提交的版本及后续回答。先用一小批审计合格样例做资源和格式试跑，再决定训练规模；本机训练占用与速度尚未实测。

### 步骤 E：分两种方式评测

1. **单步检查**：给同样的正确先前状态，测试这一步是否新增、更新或保持得当，是否引用了支持该结论的证据。
2. **连续回放**：每个系统使用自己此前产生的记忆继续运行，不在每一步重置为标准状态。检查错误覆盖、旧值残留、关联信息被误改，以及后续问题或选择是否改善。

外部对话流、负责后续回答的模型、预算和评分规则保持一致。系统内部记忆会因更新策略不同而变化，这正是实验需要观察的结果。MemOps 自带的后续问题可用于检测记忆使用；为证明**后续决策**改善，还需补充有明确约束和标准答案的小型行动／选择探针，并把它们与真实用户满意度分开报告。

## 4. 之后怎样加入其他数据源

1. **PersonaMem-v2：扩大到偏好。** 先选择普通生活偏好的文本材料，人工检查对话是否真的支持目标偏好、该偏好属于谁、是不是临时表达。以人物为单位隔离训练与测试。完整人物档案可用来核对标注，不能直接送入模型作为历史。它是生成数据，适合研究隐含偏好理解；真实选择效果仍需另行验证。
2. **LongMemEval：检查长历史系统能力。** 使用官方清理版，记录所选版本、问题 ID 和上下文预算。对正常长历史输入和只提供相关证据的排错输入分别报告结果；后者用于判断问题是否出在查找和组装历史，不能与正常条件混为同一成绩。保持它与训练材料隔离。
3. **MemoryArena：检查行动闭环。** 等第一版能稳定记录模型所见证据、动作与反馈后，再接入一类多阶段任务，观察早期经验能否改变后续行动。其环境搭建与运行成本需单独评估；不作为第一轮本机微调的前置条件。
4. **真实反馈：最后补上产品结论。** 选定具体领域后，记录展示过的候选及排序、当时约束、用户表达的理由、实际选择和之后的体验。一次点击或下单只说明行为发生，不能单独作为长期偏好或满意的标准答案。

## 5. 使用边界与记录要求

- 公开数据的对话和偏好可能由模型生成并经过自动筛选；抽样人工审计与错误分析不能省略。[MemOps 官方说明](https://github.com/MemTensor/MemOps)、[PersonaMem-v2 数据卡](https://huggingface.co/datasets/bowen-upenn/PersonaMem-v2)都说明了生成来源。
- 每次实际下载时，记录来源 URL、版本或提交号、获取日期、所用子集、转换规则及当时的许可证／使用条件。原始数据是否可以再分发，以实际来源规定为准；研究记录与代码可以引用原始来源。
- 训练样例、调试样例、最终测试和人工功能验收样例分别保存。改变了数据划分、模型、提示词、输入预算或评分方式，就在结果中写清楚。
- 结果至少分别报告：记忆更新正确率、误覆盖或旧值使用、证据支持情况、后续问题正确率、受约束决策结果，以及调用和输入成本。性能提升与真实用户满意度是不同结论。

以上为沿用并同步范围后的研究主线。以下把开发所需的适配、可见性、运行和评分接口具体化；这些接口约定不代表对应代码已实现。

## 6. 第一版数据交付物和存放方式

### 6.1 交付清单

第一版交付 10 类人工完整轨迹、20—30 条经人工审计的 MemOps 完整轨迹、转换器、分组/用途清单、可见事件流、隔离评分标签、校验报告和实际运行结果。公开数据未取得许可确认之前，不将原始数据随代码一起发布。

本次文档包的 `开发附件/manual_events.jsonl` 与 `manual_checkpoints.jsonl` 提供人工编写的格式示例和 10 条起步轨迹；它们没有经过真实模型运行，不能当成绩。它们属于人工功能验收集合，不占 MemOps 的 20—30 条配额，也不混进未来训练/最终测试。

### 6.2 目录与权限

```text
datasets/
  manifests/          # 来源、许可、原始文件哈希、转换版本
  raw/                # 上游原文件，只读；默认不提交 Git
  audits/             # 人工审查记录
  splits/             # 背景/人物分组与用途
  processed/          # 模型可见事件；回放时逐步接纳
  labels/             # gold/checkpoint；仅 evaluator 可读
  probes/             # 独立的小型选择/行动探针
results/<run_id>/      # 配置、分项结果、错误、调用与成本
```

生产/研究运行中，`labels/` 不挂载到 Agent 容器；数据库标签 schema 不授予 Agent 用户权限。开发者网页可以经有权限的评测 API 查看标签，但模型工具不可调用该 API。转换器可同时读取源和标签来生成工件，运行器与评分器的权限仍必须拆开。

## 7. 下载、审计、分组和用途冻结

### 7.1 获取清单

每次获取实际材料生成 manifest，最低字段：dataset_id、source_url、source_revision 或发行版、retrieved_at、所用文件/子集、每文件 SHA-256、license_url、license_status、允许用途/再分发备注、原始样本数量、语言、adapter_version。

上游没有明确许可时写 `unverified`，人工处理后才能进入允许的用途；不能因为 GitHub 公开可见就推断可以再分发或训练。缺失值保留 null；不要编造 revision、许可或获取日期。

### 7.2 人工审计记录

每条完整轨迹记录：`trajectory_id`、`group_id`、`reviewer_id`、`reviewed_at`、`audit_status`、`issues`、`included_checkpoints`、`excluded_checkpoints`、`notes`、`label_revision`。

`audit_status` 为 pending/pass/revise/exclude。至少检查：是否能由当时证据判断；更新主体和范围；条件与生效时间；旧值是否明确；助手确认有没有泄漏；后续问答答案是否有来源。疑难项不能无声删除，要记录排除理由和分母变化。

人工修正标签保存补丁和原标签，不改上游 Raw。测试标签修正应版本化，报告受影响的实验；不能只修正当前模型答错的标签而不重新检查其他方法。

### 7.3 分组原则

同一人物/原始背景及其相关长短版本、派生问答保持同组。上游没有 group 字段时，从背景/生成来源建立稳定分组；不能仅按文件名随机拆分。规范化文本哈希检查完全重复，背景映射检查近似关联；无法确定的样本先不进入最终测试。

首批 20—30 条为了理解标签会被人工完整阅读且用于调提示词，默认全部标为 `audit_dev`。后续扩样再在组层面冻结 `train/dev/test`；已经参与调试的组不得再成为未见测试。测试集可由独立评测者保管，或通过程序隔离，避免日常开发反复查看 gold。

第一版不强制一个在小样本上没有意义的固定 70/15/15 比例；先保证用途和背景分组清楚。实际选择的比例、随机种子、分层方法与组清单写进 split manifest。短版和长版必须复用同一分组结果。

## 8. 统一事件与检查点格式

### 8.1 两种顺序号不能混用

`source_index`：转换后同一轨迹中的源事件顺序，从 1 开始；属于只读数据工件。`event_seq`：运行时进入某个 Namespace 的接纳顺序，包含可能的工具/控制事件，由核心分配。二者不保证数值相同。

适配器维护 `source_event_id → runtime_event_id/event_seq` 映射。检查点的 `visible_through_source_index` 先解析为已接纳源前缀，再转换成该次调用的 runtime `visible_through_seq`。不能把源文件中最大序号直接传给模型工具开放未来材料。

### 8.2 模型可见事件文件

`manual_events.jsonl` / `input_events.jsonl` 一行一个事件，最低格式如下：

```json
{
  "schema_version": "1.0",
  "dataset_id": "manual_v1",
  "trajectory_id": "manual_02_update",
  "subject_group_id": "manual_person_02",
  "source_event_id": "manual_02_e3",
  "source_index": 3,
  "source_session_id": "session_1",
  "type": "user_message",
  "role": "user",
  "content": "预算改成300元，其他要求不变。",
  "occurred_at": null,
  "metadata": {"task_key": "weekend"}
}
```

role 保留 user/assistant/tool；task_control 等控制事件还可带结构化 payload。用户内容不能因为测试需要被改成 system 指令。事件文件不允许出现 expected/gold/answer_key 等评分字段；人工样例中用户的自然发言本来包含某个金额，不算泄漏。

metadata 用于适配器映射会话/任务，不必全部拼进模型提示词；人物组 ID 和文件名可能暗示标签，默认不作为自然语言背景注入。source_event_id 在轨迹内唯一，source_index 连续递增；工具 call/result ID 必须能够配对。

### 8.3 评分标签文件

`checkpoints.jsonl` 一行一个检查点，只给 evaluator：

```json
{
  "schema_version": "1.0",
  "checkpoint_id": "manual_02_c2",
  "trajectory_id": "manual_02_update",
  "trigger_source_event_id": "manual_02_e3",
  "visible_through_source_index": 3,
  "target_mode": "known_field",
  "target": {"subject_ref":"self","predicate":"activity.budget","scope_type":"task","scope_ref":"weekend"},
  "gold_before": {"amount":500,"currency":"CNY"},
  "expected_action": "UPDATE",
  "expected_value": {"amount":300,"currency":"CNY"},
  "evidence_source_event_ids": ["manual_02_e3"],
  "probes": []
}
```

target.scope_ref 是数据集内的稳定逻辑键；运行时映射到真实 Task/Session/Subject ID 后评分。`expected_action` 是本项目三类接口，不声称上游同名标签一定同义。`gold_before` 为单步诊断输入；连续模式绝对不能每步注入。

`probes` 可以包含 `kind=question/selection/state_assertion`、prompt、候选、expected、scorer 和证据。state_assertion 可检查 CTS、范围、任务状态等，不强迫所有测试都转成三类记忆动作。action 允许为 null，表示该检查点不评分更新动作。

### 8.4 原始标签映射

转换器逐版本明确列出支持哪些上游字段及枚举。未知字段/新枚举放入 quarantine，停止该样本转换，不凭字符串相似猜含义。保留 upstream_label 和 mapping_rule_version 在评分侧 provenance。

例如上游某个 update 可能指一个尚未确认的未来计划，本项目对当前值的正确动作为 KEEP；必须同时考察确认状态、原文和有效时间。Forget/Reflect 默认不进入首轮三类操作评分，不直接转换为删除数据。

### 8.5 证据引用

评分工件优先使用完整 source_event_id；需要区间时遵循主计划的 Unicode code point 半开区间约定。接纳后转换为 runtime_event_id。引用必须存在且不晚于可见上限。原文区间匹配是必要条件，不足以证明语义支持，后者仍需标签审查。

## 9. 数据适配器的函数边界

以下为项目拟实现接口，不是上游提供的现成代码：

```text
inspect_source(path) -> SourceManifest + UnsupportedFields
parse_trajectory(raw) -> NormalizedTrajectory
map_labels(raw, normalized, mapping_version) -> GoldCheckpoints
validate_trajectory(events, checkpoints) -> ValidationReport
assign_groups(trajectories, background_map) -> GroupManifest
assign_splits(groups, policy, seed) -> SplitManifest
export_visible_events(trajectories) -> input_events.jsonl
export_evaluator_labels(checkpoints) -> labels/checkpoints.jsonl
```

适配代码测试必须固定几个已审查源样本，验证角色、顺序、证据偏移、范围、长短版本分组和未知枚举行为。不要仅测试“JSON 能解析”。

最低转换报告包括：原始轨迹/事件/操作数、保留数量、未支持操作数、排除/隔离数量及理由、证据失效数、重复/关联组冲突、文件哈希、转换版本。计数满足输入 = 输出 + 明确隔离/排除，避免样本凭空消失。

下载、验证、转换与运行分开命令；转换器不得自动调用被测模型改写源数据以使它更容易答对。修复格式可以程序化；涉及语义修订必须保存补丁和审查来源。

## 10. 运行器与检查时点

### 10.1 单步诊断

为每个检查点创建新的受控状态空间；注入规定的 gold_before 和允许历史（显式标为诊断条件）；接纳触发消息；运行相同更新器/提交器；对候选和实际提交分别评分。结束后销毁或冻结，不把结果带到另一个检查点。

报告必须写 `single_step_gold_state`。它能排查“这一步判断错了”，不能代表系统从头连续维护正确状态的能力。

### 10.2 连续固定流

从空 Namespace 或明确声明的初始已知状态开始；按 source_index 接纳下一条消息；遇到检查点先评价该时刻的状态，再继续接纳后续事件。每种方法使用自己的更新结果，不纠正成标准状态。

源数据中的历史助手消息照原顺序保留。为了保持外部流一致，默认不在每条源用户消息后额外生成一个会影响后面输入的新助手回答；在指定 probes 上调用固定后续回答模型。交互展示可以另行生成，但不得混为固定流成绩。

### 10.3 Probe 隔离

检查点之后创建只读快照或隔离 probe Namespace，使用当时可见状态问后续问题/给候选。probe 的答案、评分和纠正不写回主轨迹；其调用成本计入该运行的 evaluation/probe 分类。主轨迹继续时看不到这些答案。

需要模拟反馈闭环时使用单独的明确模式，并固定反馈生成机制；不能临时让评分器把答案告诉被测模型再接着测。

### 10.4 在线与离线相同和不同之处

相同：事件、更新提交、检索、Context Builder、摘要发布、证据和权限校验。不同：外部输入来自固定轨迹还是人；是否每轮产生新的主回答；调度是否使用确定性屏障；是否有隔离评分器。差异进入 run_manifest。

## 11. 四组基线与比较条件

A 最近消息窗口；B 普通滚动摘要；C 核心上下文方案不带 TP；D 核心加 TP，定义以主计划第 20 节为准。所有方案固定后续回答模型、源事件流、候选工具结果、预算上限和评分器。

A/B 没有结构化事实表，其事实操作指标为 N/A；比较最终任务成绩与成本。不能先用 C 为它们更新一份隐藏事实，再称作简单基线。D 的主题必须在 D 自己的 Namespace 生成，不能提前离线读全轨迹生成后再按需给它。

调度使用 `deterministic_barriers` 时，在规定边界等待当前可见源所需的派生索引完成，不允许读取未来。线上异步调度的延迟实验单独报告，不与算法主对比混淆。

## 12. 判分、异常与结果文件

### 12.1 规范化与评分

金额比较数值与币种；位置/职位等字符串可用经审查的别名表；列表比较依据任务定义是否有序。规范化规则不能随被测输出临时扩展。无法确定等价的输出标 needs_review，而不是自动算错或自动算对。

三类动作分别报告准确率及 confusion counts；主计划定义的误覆盖、旧值使用、主体/范围、证据、后续问答、选择、成本都要保留分母。没有标注的额外信息不自动算误记；系统发现未标注字段另设人工审查能力实验。

### 12.2 无效、失败、未评分

`invalid_input` 表示数据/配置不满足试验条件；`system_error` 表示运行中系统失败；`scored_fail` 表示完成但结果错误；`needs_review` 表示标签或评分不确定；`cancelled` 表示被终止。不能把它们全部排除后只报剩余准确率。

至少同时展示“已评分项准确率”和“全部启动轨迹的完成/失败情况”。外部 API 故障可以重跑，但报告尝试次数及成本；不能挑一次偶然正确的结果作为唯一成绩。

### 12.3 结果记录

`case_results.jsonl` 每项至少有 run_id、trajectory_id、checkpoint_id、mode、config_hash、actual_action、actual_value、commit_outcome、source_refs、probe_result、score、score_status、failure_stage、call_ids、snapshot_ids、cost_refs。

`metrics.json` 包含每项分子/分母、分组结果、N/A/invalid/未评分数量、运行完成率。`errors.jsonl` 包含错误码、阶段、可重试与根因候选。`costs.json` 对 answer/update/episode/TP/embedding/probe/judge/repair 分开，并说明未知值和币种。

### 12.4 如何从小样本扩大

先用 20—30 条定位格式/边界问题，再扩大审计通过样本和独立保留组。改变标签规则、split、源版本或评分器时新建结果版本，不把旧成绩直接覆盖。不要从少量合成轨迹推出真实用户满意度结论。

## 13. 人工小型选择探针

首版采用有明确约束和答案的构造任务。例如，用户把预算由 300 元改为 150 元，并要求安静；候选 A=120 元但嘈杂、B=140 元且安静、C=260 元且安静。预期选择 B，理由必须使用当前预算和安静要求。

候选内容、排序、候选 ID、价格单位、约束和正确性规则固定。为检测位置偏差，可以预先生成若干固定排列并分组报告，不能只在某方法失败后替它换排序。候选集有多个合法答案时定义允许集合，不强迫一个无依据的唯一答案。

探针只验证记忆能支持受约束选择。真实体验、长期偏好和满意度需要许可下的真实反馈，不由这些构造题替代。
