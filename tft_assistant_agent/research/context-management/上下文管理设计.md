## 适用范围与生命周期

- 当前上下文管理仅服务于单个 session，不设计全局记忆或跨 session 共享。
- Raw Event Log、Episode、Task Package、Rules / Constraints、Current Task State、索引和缓存均归属于 `session_id`。
- 本文中的“永久保存 / Pin”均指 session 存续期间，不意味着删除 session 后继续保留。
- 删除 session 时，必须一并删除所有相关上下文管理数据；具体清理规则见本文末尾。

储存层：
上下文储存架构设计
1. Raw Event Log（所有上下文）       
↓ 
2. Episode 分段  （每次压缩时分段）    
 ↓
3.  E1 E2 E3 ... E100  （压缩后）
 ↓
4.  Episode Index / Memory Store

Memory Store：储存所有信息
Episode Index：储存所有 E 的索引

索引层（成本问题）
首版索引设计：
1. Vector Index，常规 embedding vector
2. BM25 Index，使用Inverted Index，用精确词汇给算分

Graph Index 保留为后续研究项，首版不构建或使用图索引。

检索层
Hybrid Retrieval + Agentic Retrieval：前者描述多种检索方法如何组合，后者描述模型何时发起和继续检索，两者可以同时存在。

### 首版两路召回（2026-10-03 已确认）

- lexical：关键词召回，使用 BM25 查找名称、路径、参数、错误码等精确信息。
- semantic：语义召回，查找含义相近、表达不同的信息。
- 两路结果采用固定融合策略，去重后按 `top_k` 与 token 预算返回；模型暂不自由调整权重。具体融合算法和参数仍待实现与验证，建立基线时固定配置。
- Graph、recency、importance 不参与首版排序。先跑通两路召回，再根据实际失败案例评估后续优化。
- 来源引用、新旧版本、撤销关系和适用范围仍须保留；当前有效性判断属于正确性要求，不依赖 recency 排序。历史查询允许读取旧版本。
- 首版工具可采用 `retrieve_memory(query, top_k, token_budget)` 草案，数量与预算由 SDK 配置和限制；映射到绑定 session 对象的 `retrieve` 方法。

检索结果作为历史证据进入 Context Builder 的历史区域；必要时附原文证据，不再新增固定上下文层。与 Recent Raw、Episode、TP 的重复内容由构建器结合来源引用处理，不修改历史事实和消息角色。

### 早期五权重设想（非首版，后续研究）

早期设想允许模型选择以下五种权重；该方案保留为研究内容，不作为首版接口和排序策略：
1. semantic_weight：语义，embedding vector
2. lexical_weight ：精确词义，BM25
3. graph_weight：关系，Graph 
4. recency_weight：越新越高，指数衰减
5. importance_weight：压缩时模型根据当前 episode 对后续任务的重要程度评分，待研究
暴露类似
retrieve_memory(
    query,
    semantic_weight,
    lexical_weight,
    graph_weight,
    recency_weight,
    importance_weight,
    top_k
)
这样的结构化的类

### 五权重研究建议（非首版，待验证）

- 如后续研究模型调权，由模型选择查询侧重点，SDK 负责把参数转换成稳定排序行为；须与已跑通的首版固定融合基线比较，不能直接作为默认能力。
- 不直接将未校准的 Vector、BM25、Graph 原始分数相加。可以比较统一尺度后的加权与基于排名的融合；具体算法和默认权重尚未确定。
- 权重须有限、非负；全零、缺省参数、未启用 Graph 等情况要有明确校验或回退规则，返回实际生效的权重和降级原因，不能静默改变含义。
- recency 表示新近程度，不等于当前有效。检索当前状态前应处理撤销、适用范围和版本；检索历史原因时保留对应时点的信息。
- `top_k` 与返回 token 预算同时限制结果；建立默认权重、模型调权的对照实验。importance 的生成方式和未来查询价值仍待研究。
- Graph 作为可选能力，通过多跳任务实验确定收益，不作为首版稳定运行的前置条件。
- SDK 接口建议将已有 `retrieve_memory` 工具映射到 session 对象的 `retrieve` 方法，工具名称可由适配器设置。

外部事实依据：Azure 的[混合搜索评分文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)说明了不同检索评分的尺度差异及 RRF 融合。获取日期：2026-09-18。上述五权重职责划分为本项目设计建议，并非该文档提供的现成方案。

## 上下文层

### 上下文组装四层结构

#### 1. Rules / Constraints

**来源：**

1. `agent.md`
2. 需求产品文档提炼
3. 对话中用户特别要求

**处理：**

- 完全不压缩，在 session 存续期间保留。

#### 2. Compressed History

**来源：**

- 已生成并成功提交 Episode 压缩结果的历史 Raw，包括从 `Recent Raw` 中迁出的已压缩部分。
- 触发压缩本身不改变事件归属；压缩结果成功提交后，才将对应 Raw 从完整上下文中移出，原文仍保存在 Raw Event Log。

**处理：**

- 使用 Main Compression Agent 处理。
- 主要工作内容是对较早历史进行压缩和整理。
- 当前方案组合：
  1. 避免 recursive compression 的分段压缩保存方案：ACM 的 Episode Summaries 优化版。
  2. 具体压缩方案：文本压缩具体方案。

#### 3. Recent Raw

**来源：**

- 尚未被已提交 Episode 压缩结果覆盖的最新 Raw 事件。
- 包括压缩触发后的用户输入、模型返回、工具调用与返回等事件；在途压缩尚未成功提交时，其来源 Raw 也仍需保留。

**处理：**

- 完全不压缩，直接放入上下文，保证高保真。
- 在途压缩期间，新增事件立即持久保存为待合并尾部，暂不修改已发布模型上下文；交接完成或显式失败回退后，再按本轮事件边界完整纳入新快照。

#### 4. Current Task State

**来源：**

- 初始化时生成；用户修改目标、工具返回、任务切换等关键事件发生时增量更新，不等待压缩触发。
- 这是唯一可以递归修改的部分。

**处理：**

- 每次组装模型输入前，确认本次快照中的关键事件已反映到任务状态。
- 压缩时可以结合压缩原因核对和整理状态；后台压缩结果不得直接覆盖更新后的状态。
- 详细字段、更新流程、任务切换与状态版本见 [Current Task State 设计](./Current%20Task%20State设计.md)。

### Context Builder 组装建议（待验证）

- 逻辑上保持以上四层；初始物理排列建议为 `Rules → Current Task State → 选中的 Compressed History → Recent Raw`，效果需通过实验比较。
- 每次模型调用都重新选择所需上下文，包括工具执行后的下一次模型调用；不能只在用户新一轮发言时运行。
- 固定加载适用规则、当前任务状态和需要完整保留的最新 Raw；历史只选与当前任务相关且预算允许的部分。可结合主动预取与模型自主检索。
- 处理 Episode、TP 与检索结果的重复和版本关系。历史回查内容保留来源标签，不伪装成当前用户的新指令。
- 保留角色和工具调用关联；工具调用及其结果不可被截断成非法消息结构。
- 预算覆盖规则、任务状态、历史、Recent Raw、工具定义、输出格式等完整输入，并预留输出 token 与安全余量。必保留内容已经超预算时，应返回明确错误或按约定降级，不能静默丢弃新要求。
- 返回不可变的本轮输入快照及事件边界、状态版本、token 用量、选取理由与降级信息。构建期间到来的新事件留给下一快照，或由宿主明确中断并重建本轮输入。
- SDK 中的具体数据契约与调用流程见 [上下文 SDK 设计](./上下文SDK设计.md)。

### 上下文压缩策略补充

1. `Raw Event Log` 在 session 存续期间保存，删除 session 时一并删除。
2. `Recent Window` 完整保留。
3. `Critical Information` 在 session 存续期间 Pin。
4. `Old Context` 异步交给 Context Subagent。
5. Subagent 使用 Keep / Snippet / Compress / Delete 等精细操作。
6. Milestone 是主要 consolidation trigger。
7. Token threshold 是兜底 trigger。
8. 每次 consolidation 都从 raw events 出发，避免 summary of summary。
9. 主 Agent 在下一轮采用新的 compressed state。

### 异步 Episode 压缩交接建议（待验证）

已确认的基本方向：一次后台压缩作业允许有限的主动召回、工具交互与模型请求。正常触发无需通知或询问用户；在途主模型请求继续执行，用户继续输入，到下一次主模型调用前完成交接。通过固定事件边界与切换视图实现，避免“清空共享列表后再补写”的竞态。具体调用预算和终止规则见 SDK 第 5 节。

1. 触发时固定旧区间，例如处理到 `seq=100`；当前模型已经拿到的输入快照不变，后台从固定 Raw 区间生成 Episode。
2. 压缩期间新事件持续写入 Raw Event Log，获得 `101、102…` 等序号，形成持久保存的待合并尾部，不即时修改已发布上下文。每条事件记录所属 turn / 调用和输入快照引用；接收顺序不等于模型已读到该事件。
3. 结果通过校验后，原子发布 Episode 及已压缩位置。Recent Raw 视图随后只保留未被提交结果覆盖的尾部；构建器按选定边界合并新增事件与匹配的任务状态，Raw 原文不删除。
4. 等待点在下一次主模型调用前，包括工具循环中的下一次调用；当前已生成的回答可先展示，接收新用户消息不等待压缩。等待完成信号时不得持有压缩提交需要的锁，只在发布或读取一致快照时短暂互斥。
5. 边界需避开未闭合工具调用；首版每个 session 只允许一个 Episode 压缩作业在途，后续触发合并或排队。TP 可独立运行且不迁移 Recent Raw。
6. 超时、压缩失败、预算耗尽或无效结果时保留旧视图与 Raw，重试计入作业总预算。若回退，先协调作业发布资格，再将未压缩 Raw 和待合并新事件完整构建为新快照；请求符合预算才可标记降级继续，否则报告无法构建上下文，不能静默遗漏新增要求。
7. 发布需检查预期已压缩位置和 session 有效性；旧作业不得重复迁移事件、覆盖新版本或在 session 删除后写回。

更具体的区间、作业与恢复契约见 [上下文 SDK 设计](./上下文SDK设计.md)。

### 轻量 Task Package

- TP 按功能 / 主题保存简单用途介绍、相关 Raw 引用和对应功能的分条摘要；常规压缩发现关联后，只通知独立后台队列读取新增 Raw 并追加，不重建完整任务快照。
- 主循环、Context Builder 和 Episode 发布不等待 TP；TP 不使用 Episode 的交接屏障，不迁移 Recent Raw，也不修改任务状态。共享资源通过低优先级和并发 / 调用预算控制。
- TP 查询按需选择有限条目并可回查原文，历史事实保留变更关系。目录可能滞后于 Recent Raw；最新要求由当前状态和 Recent Raw 承接，检索可补查尚未进入 TP 的原文。
- 完整结构、版本规则与登录功能示例见 [文本压缩具体方案第 4 节](./文本压缩具体方案.md)，发布和删除规则见 [上下文 SDK 设计第 5、7 节](./上下文SDK设计.md)。

### Session 删除规则

以下为“所有数据跟随 session 删除”的执行约束；具体存储实现待定。

1. 删除开始时关闭该 session 的新读取、事件写入和后台结果发布，使正在运行的压缩 / TP / 索引作业失去提交资格。
2. 取消并收敛后台作业，然后清理 Raw、Episode、TP（含目录、介绍、条目、来源关联和修订记录）、任务状态、规则及 Pin、所有索引条目和图关系、缓存、临时文件，以及 SDK 持有的含 session 内容的作业和诊断记录。
3. 不得只删除原文而保留可召回的摘要或向量；后台迟到结果也不得重新创建 session 或恢复已删数据。
4. 删除操作应可重试。只有所有受 SDK 管理的数据均已清理，才能报告删除完成；失败时维持不可访问的删除中状态并报告未完成项。
5. 宿主 Agent 持有的聊天副本、日志、备份或外部存储副本，须由接入方对接清理；SDK 不能把自身清理成功等同于所有外部副本已删除。
