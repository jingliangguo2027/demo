# Current Task State 设计

## 定位与范围

Current Task State 表示当前任务“现在进行到哪里、接下来做什么”，供每轮 Context Builder 使用。

- 保留原设计的五项核心信息：`task_id / goal`、`status`、`progress`、`open_items`、`next_action`。
- 仅属于当前 session。一个 session 可保存多个任务状态，通过 `current_task_id` 指向当前任务；删除 session 时全部删除。
- 状态允许递归增量更新，但每次更新应能追溯到 Raw 事件。Episode / Task Package 继续从相应 Raw 生成。
- 下面的字段扩展、状态流转和更新机制为本次按用户要求补充的设计构想，尚未实现或验证。

## 核心字段与建议扩展

| 字段 | 用途 |
| --- | --- |
| `session_id` | 数据所属 session，禁止跨 session 更新和读取 |
| `task_id` / `goal` | 当前任务及其目标；目标变更保留来源事件 |
| `status` | 原有 `active / paused / blocked / likely_complete`；建议增加 `completed / cancelled` |
| `progress` | 已完成事项及其证据；区分已执行与已验证 |
| `open_items` | 待解决事项，每项有稳定 ID，便于增量完成、重开或取消 |
| `next_action` | 根据现状提出的下一步；它是建议，不代表已执行 |
| `acceptance_criteria` | 用户或宿主给出的完成条件；推测的条件须标记待确认 |
| `constraints_refs` | 引用当前有效约束，避免与 Rules 层维护两份不一致正文 |
| `decision_refs` | 关联适用的关键决策身份；Context Builder 按本轮事件边界解析有效版本，避免重复维护决策正文 |
| `blockers` / `dependencies` | 阻塞原因和任务依赖；无内容时省略 |
| `artifact_refs` | 文件、产物、工具结果的引用，避免塞入大段正文 |
| `state_version` | 每次成功状态更新后递增，用于拒绝过期覆盖 |
| `processed_through_seq` | 已检查并处理到的 Raw 事件序号；包括检查后无需修改语义字段的事件 |
| `source_event_ids` | 本次状态更新所依据的 Raw 事件；关键 progress / open item 建议各自保留证据引用 |

字段可以逐步引入；空字段不必进入模型上下文。`state_version`、处理位置等控制信息主要供 SDK 使用。

## 更新时机

关键变化到来时更新，不能等到上下文压缩才生效。

| 事件 | 更新内容 |
| --- | --- |
| 用户新建或修改任务 | goal、约束引用、待办、完成条件及 next_action |
| 用户纠正、撤销旧要求 | 替换对应现行要求，保留事件依据，重新检查受影响待办 |
| 工具调用完成或失败 | progress、待办、阻塞项；仅发起工具调用不能算完成 |
| 获得验证结果 | 标记哪些事项已验证，哪些仍待验证 |
| 用户切换、暂停或恢复任务 | current_task_id 与相应任务状态；切换不自动代表旧任务完成 |
| 明确完成、取消或后续追加工作 | completed / cancelled，或重新激活任务 |
| Episode 压缩提交 | 可触发一致性核对；不能用旧压缩快照覆盖新状态 |
| TP 功能摘要条目追加 | 不更新任务状态；目录介绍和历史摘要不表达当前完成度，完成与进度仍依据原始事件判断 |

无需每条事件都调用模型重写整个状态。宿主已知的工具成功 / 失败等信息可以按规则更新；语义理解可合并一批事件生成 patch。用户的新目标和纠正必须在下一次相关模型调用前反映出来。

## 更新与组装流程建议

1. 事件先写入 session 的 Raw Event Log，取得稳定 `event_id` 和有序 `seq`；重试写入应幂等。
2. 读取旧状态及其版本，处理尚未反映到状态的事件，生成最小 patch。
3. 校验 patch 的字段、任务归属和证据；不得将推测写成已完成事项。
4. 仅在基准 `state_version` 仍匹配时提交；不匹配时读取新状态重新计算，不能整份覆盖。
5. Context Builder 选定本次输入事件边界，读取与该边界一致的状态和 Raw。后续新消息归入下一快照，或由宿主明确中断并重建本次输入。
6. 如果状态抽取失败，不推进处理位置，也不把旧状态冒充为最新状态；保留尚未处理的 Raw。构建器可以报告状态滞后并按配置重试或降级，不得静默丢弃新要求。

首版可以采用 session 内串行状态更新队列，简化并发；后台 Episode / TP 作业只读取状态快照，不能绕过更新入口写状态。

## 状态流转建议

- `active → paused`：暂时转向其他任务或用户明确暂停。
- `active → blocked`：有明确阻塞原因，应能指出需要的输入或外部条件。
- `active → likely_complete`：模型判断接近完成，尚缺足够证据或确认。
- `active / likely_complete → completed`：满足已知完成条件，或用户明确接受任务结束；不是仅凭模型自报完成。
- `paused / blocked / completed → active`：恢复任务、解除阻塞或追加修改。追加工作保留原历史，不把原完成事实抹掉。
- 未完成状态可转为 `cancelled`；重新开启时保留取消与恢复事件。

状态判断与 TP 更新独立：任何任务状态下，后台均可根据新增相关 Raw 追加功能摘要；无需任务完成确认，不等待 TP 才生效新要求。TP 介绍只描述功能用途，历史条目不代表当前任务状态。

## 与其他上下文层的边界

- Rules / Constraints 保存约束正文；Current Task State 引用适用约束并表达当前执行状态。
- 关键决策可采用稳定事实身份与语义版本；Current Task State 重点维护目标、进度、待办和下一步，通过 `decision_refs` 关联决策。存储中的引用在模型输入中解析为可读正文；本轮需要准确回放时，ContextSnapshot 记录实际解析到的版本。
- Compressed History 按需包含历史事实、过程和轻量 TP 的选中条目；不能因为检索到旧状态就自动替换当前状态，也不自动注入整个 TP。
- Recent Raw 保留尚未被已提交 Episode 覆盖的原始事件，包括状态更新和压缩运行期间到来的新事件。
- 压缩只改变历史的呈现方式，不决定用户要求或任务状态何时生效。
- 本文状态用于任务理解，不等于 Agent 运行检查点。工具执行恢复、重复外部操作防护等由宿主运行时负责，SDK 可提供事件与状态引用供其关联。

事实版本与状态版本各自管理：仅更新进度或下一步不产生新的决策版本。决策变更需要 Raw 依据，旧 Episode / TP 保留其历史版本；跨表示去重和数据库选择示例见 [文本压缩具体方案第 2.6.1 节](./文本压缩具体方案.md)。

## 待验证问题

1. 语义 patch 使用主 Agent 的结构化输出，还是独立状态提取器；比较成本、延迟与错误率。
2. 非关键事件的合并更新粒度，以及状态大小上限。
3. completed 的业务判定规则；模型的完成分数尚不能直接当作经过校准的概率。
4. 用连续改要求、工具失败、任务切换后恢复、后台压缩迟到等场景验证状态不会倒退或遗漏。
