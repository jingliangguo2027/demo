0.设计的核心原则

1. 所有持久压缩结果最终都从 Raw 生成，绝对避免 recursive compress
2. 召回导向的压缩，所有行为都是为了更好的可召回性，或者说面向 embedding 压缩，最大化减少代词，跨片段信息。
3. 适度原子化，以可独立理解、便于检索为目标；保留事实成立所需的条件、例外、因果、时序和依赖，允许紧密相关的信息组成一个语义单元。
4. Task Package 按功能 / 主题组织相关 Raw 引用与分条摘要，增量追加新增材料；介绍只说明功能用途，各条摘要直接从对应 Raw 生成，不递归压缩旧 TP 或 Episode 摘要。
5. 所有 Raw、Episode、Task Package 及其索引均限于当前 session；删除 session 时一并删除，不形成全局记忆。



1. 主要方向
输入一段完整 Raw Episode，输出一个适合长期存储和后续 Retrieval 的Compressed Episode E
目标是在尽可能降低 token 的同时，最大限度保存未来未知 Query 可能需要检索的信息
核心结合SimpleMem+Dense X Retrieval两篇论文的思想
即压缩后的 summary 必须符合以下四个原则：
1. Entropy-aware Filtering：删除低信息量、重复、可推导内容，保留高信息量内容
2. De-linearization：不按照原始时间线摘要，而是按语义/任务关系重新组织
3. Atomic Proposition：围绕一个核心事实组织信息，拆分粒度以保持完整含义为前提，不强求最小或完全无依赖。
4. Self-contained Representation：补齐必要主体、范围和条件；无法经济地独立表达时保留明确关系或最小关联片段，避免为消除依赖而重复展开全部背景。


2. Compression Pipeline
整体流程：
Raw Episode
    ↓
① Information Filtering
    ↓
② Information Classification
    ↓
③ Atomic Proposition Extraction
    ↓
④ Context Reconstruction
    ↓
⑤ Conflict / Change Extraction
    ↓
⑥ Retrieval Metadata Generation
    ↓
⑦ Deduplication
    ↓
Compressed Episode E

以上七阶段描述同一次压缩作业内的逻辑处理步骤，不要求每个阶段独立调用一次模型。一次压缩作业允许模型主动多次召回历史、回查原文，并在读取工具结果后继续生成；内部模型请求数、工具调用数、累计输入与输出 token 和执行时间均有有限预算。调用次数与默认预算仍待实验验证，不能把七阶段固定实现成七次独立调用。

2.0 单次压缩作业与后台执行

- 单次压缩的单位是一个作业，不是一次模型请求。作业固定当前 session、待压缩 Raw 区间及辅助状态快照，七阶段在同一作业中完成。
- 模型可通过 `retrieve` / `read_raw` 主动召回必要证据。检索限定同一 session、来源序号不超过本作业边界；较早历史用于解释和定位，边界之后的新消息不进入本次压缩输入。
- 召回结果属于作业内参考材料，保留来源，不作为新用户指令，也不直接修改主 Agent 的 Rules、任务状态或已发布上下文。
- 作业在后台执行，正常触发无需通知或询问用户。已经在执行的主模型请求可继续，回复可直接展示；新用户消息和模型 / 工具结果立即持久写入 Raw，但暂不合并到已发布模型上下文。
- 下一次主模型调用前完成压缩交接，再按事件顺序纳入待合并的新增 Raw，并选取匹配的任务状态。等待超时与失败必须采用明确策略，不能无限等待或丢弃新事件。
- 所有内部请求、工具交互、重试与候选修复共用作业预算；预算耗尽时不启动新的调用。仅有通过校验的候选结果才能发布，否则按失败保留旧视图与 Raw。

固定区间、待合并尾部、原子发布及预算的具体约定见 [上下文 SDK 设计第 5 节](./上下文SDK设计.md)。

---
2.1  Information Filtering
参考 SimpleMem 的 entropy-aware filtering。
删除低信息量内容：
1. 寒暄
2. 重复解释
3. 重复确认
4. 无意义推理过程
5. 已经被后续结论覆盖的尝试
6. 工具调用中的冗余输出
保留：新事实，决定，规则，约束，用户偏好，状态变化，错误，解决方案，参数，名称，路径，API，数字，实体关系，未解决问题
核心底线是：如果删除这句话，未来是否可能导致某个 Query 无法正确回答？

2.2 Information Classification
过滤后的信息先进行语义分类：
1. Fact
2. Decision
3. Constraint
4. Change
5. State
6. Problem
7. Solution
8. Open Issue

这些分类可作为 proposition 的类型标签。同一事实可以带多个标签；不要求在 propositions、decisions、constraints 等字段中分别维护相同正文，分类视图可引用同一记录。当前生效的约束正文继续由 Rules / Constraints 管理，历史记录保留其来源及当时范围。

2.3 Atomic Proposition Extraction + Context Reconstruction
把分类的信息整理成适合检索且尽可能自包含的 proposition，按以下原则控制粒度：
1. atomic：围绕一个核心事实，必要时包含紧密相关的条件和结论；拆分不应改变事实含义。
2. Self-contained：补齐主体、任务、适用范围和必要背景，使片段可独立理解；不强求消除所有关系依赖。
3. Contextualized：保留条件、否定、例外、因果、先后顺序和确定程度。无法在单条中完整表达时，保留关联记录引用，检索时按需带入必要片段。
4. 对独立表达造成的大量重复背景，可采用共享背景引用或小型关联信息组；引用必须能在同一 session 中解析，不能成为断裂的上下文。

例如，原文“只有连接测试通过后，才允许切换到 PostgreSQL”应保留为一个含条件的语义单元；不能拆成“连接测试通过”和“切换到 PostgreSQL”，把条件或计划写成已经发生的事实。

2.4 Change / Conflict Extraction
针对长任务最容易出问题的：“要求修改”问题专门优化，专门抽取：
changes:
  - old: 阵容：巨龙九五
    new: 阵容：裁决婕拉
    reason: 来金锅锅了
同时检索时应默认current > previous，

补充适用范围：这里的默认优先级用于查询当前事实；查询历史决策、变更原因时，应按问题对应的时点读取旧版本。记录写入较新不代表内容仍然有效。

对关键决策和约束，可使用稳定的 `fact_key` 标识同一事项，并用 `fact_revision` 标记其语义版本，保留 `supersedes` 与来源引用。明确修改或撤销才改变有效版本；重复摘要、重新索引或 TP 再次提取同一事实不产生新的事实版本。版本替代由 SDK 校验并提交，不能仅凭摘要生成时间或模型给出的版本号认定新事实有效。含义或范围不明确时保留候选冲突和原文，不能强行合并。

2.5 Retrieval Metadata
除了正文 Proposition，每个 episode再额外生成 Retrieval Metadata，具体字段暂时定为entities，keywords，topics，types。
例如：
entities:
  - AuthProvider
  - SessionStore
  - initSession
  - restoreSession

keywords:
  - authentication
  - session initialization
  - session restoration
  - API deprecation

topics:
  - authentication migration

types:
  - API_CHANGE
  - DECISION
2.6 Deduplication
Atomic Proposition 很容易产生重复：
initSession() is deprecated.
initSession() should no longer be used.
The old initSession() API cannot be used anymore.
应该合并成：
initSession() is deprecated and should no longer be used.
但不能为了去重合并两个独立事实。上述示例仅在原文同时确认弃用与禁用、且适用范围一致时成立；`deprecated` 本身不能推出禁止使用。

2.6.1 跨表示的事实身份、版本与上下文去重

以下为本次确认方向后的工程细化，字段命名与识别策略仍待实现验证。Raw 继续作为事实依据；事实身份与有效版本是现有记录上的元数据及可重建索引，不增加第五层上下文，也不要求独立部署事实服务。

1. 首版优先给关键决策和约束分配稳定 `fact_key`，作用域至少包含 session、任务或适用对象与事项；普通正文无须全部建立事实身份。
2. 关键记录建议包含 `fact_key / fact_revision / kind / content / scope / source_event_ids或source_raw_spans / supersedes`。`fact_revision` 表示同一事项的语义版本，不等于 Task State 的 `state_version` 或 TP 的 `revision`。
3. 同一事实被多个 Episode、TP 或分类视图引用时，可共享身份与版本。summary 是概览，不作为独立的权威事实副本；决策与约束的分类视图可通过引用读取正文。
4. Current Task State 重点保存目标、进度、待办和下一步，通过引用关联适用决策与约束。Context Builder 在本轮事件边界内解析引用，向模型展示可读正文，不能只给孤立 ID，也不能读取该边界之后的更新。
5. Episode 与 TP 保留其来源时点的历史记录。当前查询选择本轮边界内有效版本，历史查询按问题时点选择；不为统一当前答案而改写旧摘要。
6. 构建上下文时比较事实身份、版本、适用范围和具体内容，避免同一事实从 summary、propositions、分类视图、TP 和任务状态重复注入。无法确认等价时不做破坏性去重；保留不同的条件、原因、结果和独立事实。
7. 不能仅按 `source_event_id` 去重：同一事件可能包含多条独立要求。历史记录的去重也不能删除 Recent Raw 中必保留的新要求、完整消息或工具调用与返回；优先减少其他区域中的重复展示。
8. 所有事实元数据、引用和索引限于当前 session，随 session 一并删除。

例子：任务 T1 的用户先选择 SQLite，后来明确因多进程写入需求改为 PostgreSQL。

| 事实标识 | 版本 | 内容 | 来源与替代关系 |
| --- | --- | --- | --- |
| `T1.database_choice` | v1 | 选择 SQLite | Raw 用户消息 R1 |
| `T1.database_choice` | v2 | 选择 PostgreSQL，原因是需要多个进程同时写入 | Raw 用户消息 R2，替代 v1 |

旧 Episode 和旧 TP 仍可保存 v1；新 Episode 记录 v2；Task State 保存“连接模块尚未实现，下一步实现连接”并关联数据库决策。当前执行查询的模型输入展示有效的 v2 决策及任务进度，历史区域不再重复注入相同决策。用户询问变更原因时，再选择 v1、v2 和变更依据。数据库密码不能写入代码等独立约束仍需完整保留，不因与数据库决策来自同一条消息而被去除。

若 v2 的用户消息仍在 Recent Raw 中，优先保留原消息，在其他区域避免重复展示同一决策；查询历史原因时才补充需要的旧版本。这些处理仅影响模型输入选择，不删除 Raw 或旧快照。

2.7 摘要错误、证据与保真（本轮补充，待验证）

旧摘要有两类不同问题：一类是当时正确、后来被修改或撤销；另一类是摘要生成时就遗漏条件、误解归属或改变了事实的确定程度。

| 问题 | 示例 | 处理建议 |
| --- | --- | --- |
| 内容过时 | 原来采用 A，后来用户改成 B | 保留变更关系、时点和适用范围 |
| 条件丢失 | “测试通过后采用 A”被写成“已经采用 A” | 保留条件，区分计划、执行、验证 |
| 归属混淆 | A 任务的决定被写入 B 任务 | 引用来源事件，明确任务和实体 |
| 例外遗漏 | 保留总体方案，却漏掉仍有效的例外 | 检查约束覆盖率，必要时回查 Raw |

- read-only conditioning context 只能避免修改旧摘要，不能避免模型采信旧摘要的错误。旧摘要可用于解释和定位，新持久事实应由相应 Raw 支持。
- 每条重要 proposition 建议附 `source_event_ids / source_raw_spans`，并标记观察、用户要求、计划或推测等来源性质；跨 Episode 补全信息也要保留其实际原文依据。
- 每个 Raw 引用必须可解析到同一 session 内的稳定事件和片段；无依据的推断不升级为已确认事实。
- 即使不递归压缩，单次压缩仍可能失真。先检查结构、来源引用和关键约束，再通过抽样人工检查与任务评测验证语义；不得把模型自检当成保真保证。
- 仅保留 Raw 还不足以保证可找回：摘要漏掉关键词后，仍需按 Raw 的关键词、实体或事件区间发现原文，而非所有回查都必须先命中摘要。
- “未来任意 Query 均不受损”保留为理想目标；可执行验收应指定必保留信息和代表性任务，衡量证据召回、错误率与任务完成效果。
- 外部工具或文件中的指令性文本保留为来源数据，不能在压缩后自动变成 Rules 或获得更高指令优先级。

外部事实依据：Anthropic 的[上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)指出，过度压缩可能丢失后来才显得重要的细节。获取日期：2026-09-18。上面的错误分类与检查机制为本项目分析和建议，尚无本项目实验结论。

## 4. 轻量 Task Package（当前采用方案）

确认日期：2026-10-03。本节记录本次讨论确认的设计方向，尚未实现或验证。首版 TP 采用按功能 / 主题组织的材料集合；原完整任务快照、完成检测和大小修改版本方案保留在本节末尾的历史研究内容中。

### 4.1 定位与结构

每个 TP 保存一个稳定的功能 / 主题标识、一段简单介绍，以及相关 Raw 编号与各 Raw 中该功能相关的摘要。介绍描述功能用途，例如“登录功能负责身份校验和登录会话创建”；当前数据库、完成状态、进度和下一步由有效决策与 Current Task State 表达，不写成会随任务推进过时的介绍。

一个功能可以跨越多个 Episode 和任务阶段；同一 Raw 也可关联多个 TP，各自只摘要与对应功能有关的内容。所有关联仍限于同一 session。

以下字段名称为实现草案，编号与范围为示例：

```yaml
session_id: S1
tp_id: TP-login
topic: 登录功能
introduction: 负责身份校验和登录会话创建。
revision: 3
entries:
  - entry_id: login-raw101
    raw_id: Raw101
    source_raw_spans: ["Raw101:12-38"]
    summary: 最初采用 SQLite 保存登录会话。
  - entry_id: login-raw137
    raw_id: Raw137
    source_raw_spans: ["Raw137:20-45"]
    summary: 因多进程写入需求，改用 PostgreSQL，替代此前的 SQLite 方案。
  - entry_id: login-raw158
    raw_id: Raw158
    source_raw_spans: ["Raw158:5-26"]
    summary: PostgreSQL 连接测试失败，发现超时配置问题，尚未验证修复。
```

Raw 编号与片段范围必须可解析到稳定的原始事件。单个 Raw 涉及多个功能或后续继续追加内容时，使用已固定的相关片段范围，不能只凭一个可变 Raw 容器编号判断来源和重复。

### 4.2 关联发现与增量更新

1. 常规 Episode 压缩发现本次 Raw 与某个功能 / TP 有关时，产出候选关联与 Raw 引用，交给独立 TP 后台队列；没有对应 TP 时，可按识别出的功能建立目录和简单介绍。关联识别方法与创建规则仍待验证。
2. TP 作业固定本次新增 Raw 引用和片段范围，读取对应原文，生成该功能相关的分条摘要。Episode、旧 TP 和介绍可辅助定位与理解，但新摘要的事实必须由本次相应 Raw 支持。
3. 摘要保留条件、来源、否定、实际验证状态与变更关系。例如明确记录“PostgreSQL 替代 SQLite”，不能只列出两个数据库名称，也不能把工具调用发起写成执行成功。
4. 校验 session、来源、条目归属与重复后，只追加新 Raw 引用及摘要，保留旧条目的历史内容。正常更新不重读全部任务历史，不重新生成整份 TP，也不递归合并旧摘要。
5. 按“同一 session + TP + 稳定 Raw 片段范围”处理重复触发与重试；同一来源成功追加一次，才更新已处理记录。一个来源关联多个 TP 时，每个 TP 独立记录。
6. TP 作业失败保留已发布条目和 Raw，按自身预算有限重试。新增关联可以合并排队；首版同一 TP 的更新可串行执行，避免相互覆盖。

关键事实可沿用已有 `fact_key / fact_revision` 与来源引用；同一事实再次出现在 TP 中，不自动产生新事实版本。当前事实的有效版本选择与跨表示去重继续遵循第 2.6.1 节。

### 4.3 与主循环、常规上下文压缩隔离

```text
常规 Episode 压缩：固定 Raw 范围 → 生成 Episode → 提交 Episode
独立 TP 后台队列：收到 Raw 引用与关联线索 → 读取 Raw → 生成功能摘要 → 追加 TP 条目
```

- 主循环和下一次主模型调用不等待 TP；Context Builder 可以读取已经发布的旧条目，不将 TP 作业加入 Episode 的交接屏障。
- 常规压缩只提供关联线索与来源引用，不承担 TP 功能摘要生成；Episode 发布与 TP 发布之间没有相互等待。TP 的成功、失败和重试不决定 Episode 能否提交。
- TP 不修改 Episode 覆盖位置，不清空或迁移 Recent Raw，不更新当前任务状态，也不替主 Agent 执行功能任务。
- TP 使用低优先级后台调度，并限制并发、模型请求、累计 token 和执行时间。共享模型额度或执行资源时，应保留主循环所需容量，避免后台作业间接抢占主请求。
- 执行隔离保留必要的数据关联：TP 仍使用同一 session 的 Raw、来源身份和删除资格检查。session 删除开始后，候选条目和迟到作业均不得发布。

队列通知的持久保存、崩溃恢复和资源配额是实现问题；具体机制待验证，不把内存通知或独立进程本身视为可靠性保证。

### 4.4 查询、时效与上下文组装

TP 通过简单介绍帮助定位功能，再选择与查询相关的条目；必要时沿 Raw 引用回查原文。限制返回条数和 token，不自动把整份 TP 或所有条目塞进主模型输入。

当前事实查询结合有效决策和 Current Task State；历史原因查询按来源时点选择旧条目与变更关系。历史条目不可因介绍或目录修订较新就升级为当前事实，也不能自动获得用户指令权限。

TP 默认在常规压缩发现关联后异步更新，因此可能滞后于 Recent Raw。最新未压缩内容继续由 Recent Raw 与任务状态承接，检索保留补查这些原文的路径。一个 TP 已有新条目，不代表该功能此前的全部 Raw 均已被发现或处理。

查询返回选定条目的固定内容、来源和目录修订；后续追加不修改已发布的 ContextSnapshot。与 Episode、Recent Raw 或其他视图中的相同事实按第 2.6.1 节处理，不破坏工具消息协议。

### 4.5 发布修订与生命周期

首版只需一个目录发布修订 `revision`：每次成功追加一批条目递增，用于识别查询时的已发布视图。它不表示功能完成度、事实新旧或原文完整覆盖；不再以修改大小同时维护 `version + revision`，也不维护“旧正文 + update 列表”的完整任务快照。

`entry_id` 与固定 Raw 引用用于条目身份、去重和回放；事实语义版本与任务状态版本仍各自管理。TP 追加不会因目录修订增加而更新任务状态或改写旧事实。

关闭时等待或取消并收敛 TP 作业，保留可恢复的已发布数据；删除时清理目录、介绍、所有条目、来源关联、修订记录、作业、索引和缓存。发布前校验 session 有效性，迟到结果不能恢复已删除 TP 或 session。

### 4.6 待验证问题

- 功能归属、已有 TP 匹配和新 TP 创建的准确性；评估漏关联、误关联和一个 Raw 涉及多个功能的场景。
- 分条摘要的粒度、长度、保真及变更关系；比较仅 Episode、Episode + 轻量 TP 的最终任务效果与总成本。
- TP 积压、延迟、通知恢复、重复追加及删除竞态；验证慢作业或失败不形成主循环 / Episode 的等待依赖。
- 介绍和条目检索的效果，以及 TP 未更新时补查 Recent Raw 的策略。

4. Task Package
4.1 简介
Task Package 是独立于 Episode Compression 的第二种压缩。
它解决的问题是一个完整阶段任务的信息散落在多个 Episode 中，如何形成一个统一的高层记忆单位
例如：
E3 讨论 authentication 架构
E6 发现 initSession deprecated
E9 修改 AuthProvider
E12 测试 migration
E15 最终完成
虽然它们在时间上分散，但语义上高度内聚
而且完整总结一个阶段任务对后续开发有很大帮助

Task Package 的触发条件包括阶段里程碑、任务暂停 / 切换、明确完成，以及主动请求保存阶段快照。它从当前 session 内、指定事件边界之前与该任务相关的 Raw 生成，不要求整个任务已经完成。

阶段快照与完成版 TP 使用同一组织方式；保存快照不会自动把任务标记为 completed，也不会清空或迁移 Recent Raw。

Episode 压缩和 TP 生成可以并行异步执行。TP 不占用主 Agent 的上下文压缩交接屏障；但发布到共享存储、更新索引和 session 删除之间，仍需检查 session 是否有效及来源版本，防止迟到结果覆盖新结果或恢复已删除数据。

4.2 Task Package Generation
Task Snapshot / Completion Triggered
（阶段快照触发，或检测到任务完成）
        ↓
Identify Task
(确定当前 session、任务和来源事件边界，查找相关 episode 及尚未压缩的 Raw)
        ↓
Retrieve Related Episodes and Recent Raw
(例如找到 E3 / E6 / E9 / E12，以及尚未进入 Episode 的任务相关 Raw）
        ↓
Locate Corresponding Raw Episodes
（根据 E，找到 raw：Raw3 Raw6 Raw9 Raw12）
        ↓
Extract Task-related Raw Spans，Task-level Compression
（根据任务相关的所有上下文，根据和常规压缩一样的压缩思想）
        ↓

TP 的检索和抽取必须覆盖尚未生成 Episode 的相关 Raw，不能只通过已有 Episode 查找，否则刚完成的阶段可能被遗漏。后台生成期间新发生的事件留待下一次快照，当前快照应明确其来源边界。

4.2.1 Task Completion Detected（历史设想；自学习部分暂缓）
根据 2026-10-03 的讨论，以下任务完成阈值自学习、根据用户反馈自动升降阈值及由此触发追问的策略，暂不加入首版，也不纳入当前调研排期。仅保留旧设想，待基础流程稳定后另行讨论和安排；其中的概率、初始阈值和调整规则均未验证。现有任务状态判定与轻量 TP 更新不依赖自学习；历史阶段快照也不依赖完成确认。
  实际场景中，一个长任务确实是由多个阶段任务构成的，但是往往任务完成时用户不会明确表示刚才的任务可以了，现在我们推进下一步。因此除了最基础的明确语义触发的 tp 压缩，当出现任务突然切换，而且切换前的任务（a）完成度较高时，应该给出一个 任务 a 完成的概率，根据概率和自学习的参数决定是直接压缩，追问，还是无视。
  1. 最开始的不会直接压缩，当模型认为压缩概率大于 x 1 时（可以从 80 开始尝试），触发追问工具，不会阻塞主进程，只是添加一个询问，概括刚才的任务，询问是否完成。
  2. 当 x 1长期正确，可以作为安全值，下调 x1到x2，x1 以上的以后直接触发压缩，x1-x2调用工具，小于 x2 无视
  3. 当 x1 长期不正确，改为上调，流程同理
  4. 可补充，如果询问长期否定，可能用户有非常高的 agent 使用能力，自己通过公共文件和 session 管理上下文了，或者当前场景不适合 task 模式，直接禁用功能。
上个任务完成的概率判断可以从以下几个方面加权：
  1. 明确完成语义（100%，其他的不同判断了）
  2. 原目标完成程度 
  3. 是否仍有 open items 
  4. 用户是否开始稳定推进另一个任务
  5. 后续是否还有回到旧任务的迹象
  6. 新任务是否是旧任务的某种补充，或者拓展
  
  

4.2.2 阶段快照补充设计

以下为按用户要求新增的阶段快照构想，具体阈值与存储实现待验证：

1. `snapshot_kind` 区分 `stage / completion`；`status` 保存来源时点的任务状态，阶段快照可以仍是 active / paused / blocked / likely_complete。
2. 固定 `source_cutoff_seq`、`source_state_version` 和实际 `source_raw_spans`。cutoff 是来源上界，不表示该范围内所有事件都属于本任务。
3. 每次发布使用独立 `snapshot_id` 和递增 `revision`，保留旧快照。较早来源的作业晚完成时，不能把“当前快照”指针回退；同一任务首版可串行生成 TP，简化发布顺序。
4. 任务恢复或被追加修改后，从相应 Raw 生成新快照，不通过递归压缩旧 TP 推导新事实。
5. 生成失败时保留已有快照与 Raw；TP 作业失败或取消不得阻止当前任务继续接收事件。session 删除则必须停止接收新事件，并拒绝后台结果回写。
6. 所有阶段快照、完成版、历史 revision 和索引都归属 session，随 session 删除。

4.4 Task Package 与 Episode 的关系
Task Package本质上也是一种Episode，但是其和普通 Episode 最大区别是
  1. Episode代表这段时间的任务总体情况，强调时序性
  2. Task Package代表某个任务的总体情况，强调同一任务。因此 Task Package的原文来源可能来自很多段 Episode，一个 Episode 也可以属于多个TaskPackage
4.5 Task Package Retrieval
Task Package 主要服务于以下四种类型的 Query：
1. Task-level
2. High-level
3. Multi-episode
4. multi-hop

因此 Task Package 本质上同时承担对任务的语义概述与任务原文召回 routing 两个作用
4.6 Task Package Update
任务完成后，再去修改任务是非常常见的，为了避免 recursive compress，每次对已完成任务重新修改后，给当前任务的 tp 的 update 字段添加修改内容，如果是较大修改，需要添加 version+1。

补充：上述 `version` 保留为较大修改的内容版本；每次发布（含小修改）另增加 `revision`，便于区分后台结果。`update` 必须引用此次修改的 Raw 和来源边界，不能作为脱离 Raw 的新摘要事实来源。需要整合正文时从相关 Raw 重新生成；旧快照保留其当时的状态，新状态由 Current Task State 表达。
